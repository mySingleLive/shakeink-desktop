## 结论

**通过，可进入 RED 测试实现。** CI-01 已将原先“>6 项”收紧为 24 项与实际中途提交同步，能够覆盖当前三个角色夹具遗漏的时序；CI-02/03 保留默认目录与服务端负例，避免用取消校验换取成功；CI-REAL 的默认全选、零失败/跳过、关系完整性和下一步骤边界正确。未发现阻止实现的用例设计问题。

## 实现时必须保持的细节

1. CI-01 的同步门应只放行前 8 个**成功返回**，其余 `generate` 返回等待主测试确认 journal 已包含这 8 个角色及其未解析关系。有些 worker 的下一请求可能在第 8 项提交前已生成快照，允许这些请求已进入 `generate`；24 项保证门放开后仍有新的快照。断言至少一个后续实体请求发生在中途提交之后，避免误测为“所有请求都在提交前组装”。
2. 关系目标须是按实际候选/任务顺序确定的最后一个，确认它不在前 8 个已提交角色内，不依赖展示名字符串的排序猜测。前 23 个指向最后一个、最后一个回指第一个，可同时验证前向关系与合法角色关系环；这些关系不能被当作父级循环拒绝。
3. 所有同步等待必须有短而明确的上限，失败时 `finally` 放开同步门，保证旧实现跑 RED 时不会挂住测试。RED 应保留实际任务错误或步骤状态，不只断言“没有到下一步骤”。
4. CI-02 可以调用控制器的私有快照方法作定向单元验证，但 CI-01 必须通过正式公开 action 和真实 `runImportAi` 校验链。CI-02 的显式空目录只测试快照选择语义，不应被解释为服务层接受了带引用的空目录。
5. CI-03 的错类型目录中放置一个合法 scene 元数据对象，并让关系引用它的 ID；否则可能只测到目录本身结构错误。正确角色目录的正例应断言返回关系 ID 保持不变。
6. CI-REAL 成功判定要求角色 task 与 artifact 按候选 ID 一一对应、所有角色 task done、failed/skipped 均为零。暂时失败重试须保留首次错误、重试原因与次数；若出现可重复的产品错误，继续修复并重新独审，不能仅多次重跑到偶然成功。

定向既有用例、类型检查和真实 Electron 证据均应分别记录结果；这里的“通过”只指测试设计通过，不代表这些步骤已执行。

## 第二阶段：CI-05/06/07 与真实运行及时暂停

日期：2026-10-30。对照 242 第二阶段已审方案，审核新增用例文案及 CI-REAL 的及时暂停要求。仍为用例设计审核，未读取真实数据或执行尚未实现的用例。

**补充用例通过，可进入 RED/GREEN。** CI-05 覆盖请求目标及响应精确单项契约；CI-06 覆盖别名可见性、可信确认类型和普通阶段不回归；CI-07 明确经过实际生成桥，能够证明有限 schema 纠错，而不是把 controller 的拒绝吞掉后自判成功。真实非瞬时失败及时暂停、保存现场并修复后新建完整会话符合验收范围。

实现须保留以下可核验断言：

- CI-05 的请求负例应分别检查 `runImportAi`、直接 schema 工厂及直接 `generateImportAiJson` 的前置拒绝，断言 model resolve/generate/generateText 均未执行；覆盖 semanticVersion 缺失、目标缺失、错阶段/intent、外部及重复 ID、kind 不一致，错误消息不得包含原文或动态秘密值。正确请求应检查 controller 生成的目标与实际候选数据相等，不能只检查字段存在。
- CI-07 的每种首轮非法输出独立建例：收集 generateText 的输入提示与调用次数，要求恰好两次，第二次提示包含固定单目标结构反馈；最后只有一项且 ID/name/kind、关系和证据与正确输出一致。两次均非法时在测试最外层 `assert.rejects`，并断言恰好两次；不能把断言放到 controller 捕获的 AI handler 中。
- CI-07 的取消、授权及网络错误用抛出的异常证明：仅一次 generateText 调用、最终拒绝而非返回默认/空资料；这些异常不能转成结构反馈后调用第二次。若错误由 runImportAi 的授权前置门抛出，则生成次数应为零。两类路径应分别写清口径。
- CI-06 必须让 canonical name 在当前 units 中确实不存在，只有已确认 alias 存在，并解析 payload 断言目标和必要祖先仍保留；不是用自由 instruction 中重复的全目录文字来通过可见性断言。普通阶段继续采用原有精确 payload/prompt hash，不能改 expected hash 迁就变化。
- CI-REAL 驱动应在 import-char 正在 running 时也检查已观察到的失败，而不只在最终 waiting 状态检查；发现结构/身份/引用/目标错误后，经真实暂停动作等待工作排空，再保存失败状态、错误、任务分布与截图。限流等已审暂时错误仍按明确白名单有限重试。暂停/重开本身不算任何角色导入成功。
- 最终成功须提供候选 ID、实体任务 candidateId 与角色 artifact ID 的一一对应关系及全状态分布，而不只给三者总数。`observedEntityCalls` 仍只能称为观察到的调用记录。

补充用例不要求修改通用生成器的重试上限，不允许用增加无界循环、占位角色或删除关系满足“全部成功”。

## 第三阶段：CI-08/09 服务层结构错误的有限纠错

日期：2026-10-30。审核新增“服务端结构错误与字段纠错边界”用例，对照 242 第三阶段已审方案。仅审核用例设计，未读取真实数据、执行真实模型或认证 r3 结果。

**用例通过，可进入 RED/GREEN。** CI-08 的实际四层链及“两个请求、三次生成恢复 / 两个请求、四次生成拒绝”能证明 controller 的一次纠错覆盖服务层 schema 异常，同时明确不放宽单个 generateJSON 的两轮上限。CI-09 对权限/网络/取消/预算/持久化的排除和 RB03/RB04 的严格证据负例保留正确。

实现测试时需具体断言：

1. CI-08 只替换 generateText，目标错误由真正的请求绑定 schema 触发并经真正的角色字段错误脱敏映射抛出，不能在 fixture 直接手抛同名错误替代跨层正例。按目标 candidateId/operationId 分组计数，避免把其他并行角色的请求误算进三次/四次生成。
2. 前两轮非法对象仍使用正确 ID/name/kind/确认 roleType，只有 reliability 和 sourceUnitIds 非法，使 RED 对应本轮实际字段门；第三轮合法对象的所有关系/证据与预期完全相等。断言首次非法对象未提交、最终无被本地“修正”的 reliability 或来源 ID；持续非法时该角色没有 artifact、task=failed。
3. 第二次 controller 请求的 instruction 只能追加固定纠错说明及允许的标签；原 entityTarget、单位、目录、作者确认类型和授权范围不变。使用不属于白名单且包含合成秘密哨兵的错误反例，断言既不重试，也不把该消息拼入任何新提示。
4. CI-09 的每种排除错误单独建例，明确发生在获取响应前、获取后模型授权复核、预算前置或运行时证据写盘哪个位置。至少有一条走真实 controller/ai 边界；断言相应目标没有第二个 controller 请求，若前置阶段未调用模型则次数为零，若供应商调用已开始则为一次。不能只让一个纯分类 helper 返回 false 就声称端到端不重试通过。
5. 原 NIW-C41 的已返回原生结构失败仍仅再请求一次；NIW-C33/47/50、RB03/RB04 等按文件实际 test ID 定向复跑，不能以一个暂停冒烟覆盖持久化与证据边界。单次生成桥 CI-07 继续恰好两轮。
6. entity 固定提示的 reliability 省略/四值规则与单位 ID 命名空间应在可信固定提示中断言，ordinary 阶段既有 hash 不得重写。RB 未知单位和虚构引文最终仍拒绝，不能因新增重试机会改变“拒绝非法输入”的最终预期。

真实导入仍要求全选、全部角色成功且零跳过；内部纠错次数与最终可见失败分开记录。测试设计通过不代表真实模型会在四轮内成功，也不允许靠清洗坏字段、删关系或手改 journal 取得成功。
