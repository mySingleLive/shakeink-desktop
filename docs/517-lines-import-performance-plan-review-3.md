## 高

1. **高2 只修了一半：`revise` 清空线索 coverage 时不清 `w.lineRepairs`。** `revise` 删除了 worldline/narrative 的 coverage（`desktop/main/novel-import.ts:1342`），也清空了 `w.dropped`（:1340），但没有 `delete w.lineRepairs`。只有 retryKind（:1197）和无清单分支（:1316）会删除它。`wizardApplyPatches` 走的是 `revise(firstList,true)`（:1317），第21步改正文后也会进入这条路径。重跑时 commit 会在旧值上继续累加（:1049），步骤完成时 recordLinesRepairs（:1016）给作者的丢弃数会偏大。这违反了“只在 coverage 被清空时清零”。
   建议：在 :1340 同一行加 `delete w.lineRepairs`。更稳妥的做法是凡是删除 `s.coverage.worldline/narrative` 的地方都同步清零（含 :1433/:1742/:1815/:1840 的 `s.coverage={}`，如果这些路径对向导可达）。补一条用例：完成第17步并产生计数，返回人物清单后重跑，断言计数只来自新一轮。

## 中

2. **中4 的方案措辞与身份规则不符；代码行为是对的，但缺反向用例。** 方案写“chapterIndex 不同时按身份规则本就不合并”，实际叙事点身份是 `artifactKey`=kind+name（`desktop/core/novel-import.ts:264,267`），`wizardLineIds` 也按名称复用已存 id（:79-83）。所以跨章同名叙事点**会**匹配，并在 chapterIndex 上产生冲突。min 不生效，是因为“整条候选无冲突才应用调和值”（:335-341）。结论成立，但理由写错了。LP-16d（test:207）只测了同章无锁的情况。
   建议：把理由改为“chapterIndex 不同会产生冲突，冲突的候选不应用任何调和值”。再补两条用例：不同 chapterIndex 时保留冲突且 order 不取 min；order 被锁定时仍报冲突。
3. **中3 的预算只限制请求总数，没有限制尾部时长，也没有对应用例。** `extra=queue.length`（:1063）。检查在扣减之前（:1070），一次拆分会扣 2，所以最多超出 1，可以接受。但最坏情况仍是 4 个串行轮次（原批→拆→再拆→重跑），按单次 50–80 s 计，会超过 120 s。LP-08b（test:245）只断言单个原始批次 ≤11 次请求，没有覆盖“步骤级预算耗尽后下一次失败即失败”。
   建议：补一条用例：多个批次各失败一次，断言额外请求总数 ≤ 初始批数，耗尽后步骤失败且 stepError 不含原文。真实 E2E 每轮记录总请求数、拆分数和最大深度（review-2 中3 的这项要求在修订小节中没有写进去）。

## 低

4. **§3R4-2“结果与发送顺序无关”说得过头。** 合并在检查点内串行，没有覆盖丢失，这一点成立。但新条目的 id 取自先提交批次的首单元（:83），冲突 hash 中 previous/value 的位置、people 并集的顺序（:315），以及 contextArtifacts 里能看到的同步骤已提交条目（:2083），都取决于完成先后。这种依赖在 3R4 之前就存在，LPT 没有引入新的不确定性。建议把措辞改为“合并正确性与完成顺序无关；id 与冲突的呈现顺序本来就不确定”。
5. **二分查找本身正确，但有一个退化边界。** 下界取最大片段，上界取 min(profile, 总字数)，且不小于下界（:69）。贪心按序装箱的批数随 C 单调不增，所以二分必然终止，并得到“批数 ≤ 目标”时最小的最大批。maxUnits 在 pack 中单独检查（:67）。整章不拆，只有超出 profile 的章按 profile 切（:66）。问题在于：只要有一章超出 profile，切出的片段约等于 profile 上限，下界就被抬到 profile，均衡失效，退回“填满到上限”。建议把超大章按“不超过当前 C”切分（在二分中重算），或者先以不切大章求出 C，再把大章按 C 切。《诡秘之主》第1卷各章远小于 profile，暂不影响。
6. **fit() 对半拆分后不重新排序。** `queue=plan.sort(...).flatMap(fit)`（:1036），半批留在原批的位置上。世界线 ≤31 批、31 个 worker（:1080）会一次全部发出，LPT 对世界线实际不起作用，只影响叙事线。建议先 flatMap(fit) 再排序，代价可以忽略。
7. **高1、低5、低6、低8 已落实。** 未知 narrator 删除后计入 droppedLinks，不写 attribution（`desktop/service/novel-import-ai.ts:1258`，LP-23c）。id 避让检查会话全部 id 与本批已分配 id，循环上限为 |held|+1 次，超出抛错（:80-82，LP-25）。linesRepairs 每次生成前重置（service:688），严格 schema 要求非负且合计>0（:1140-1146），主进程按车道白名单（main:1733），LP-26 覆盖。唯一名的判定是精确且唯一，不用别名（service:1227），重名计为丢弃（LP-26）。schema 与 `dropped.kind:'lines'` 见 `desktop/core/novel-import-wizard-state.ts:24,31,49,65`，Notice 见 `NovelImportWizard.tsx:193`。还有一处可以加强：LP-23c 只断言规范化输出没有 attribution，建议再断言 `validateImportSemanticArtifact` 拒绝这一条。
8. **低7 作为已知限制可以接受。** 调试行只输出字段路径与计数，没有新的原文、模型输出或 Key 外泄路径。

## §3R5 慢批提前拆分（方案审核，代码未写）

- **高A：被取消的一路会被当作步骤失败。** `cancelAi` 让 ai() 以“导入操作已取消”拒绝。`worldEntryRerunnable` 不匹配这条消息（`main/novel-import.ts:118`），runJob 会直接抛出，worker 随即设置 halt（:1066-1068,1079）。暂停取消的也是同一条消息，所以不能按消息区分。建议：取消前在内存组状态中把该 Job 标记为 superseded；runJob 的 catch 第一步检查这个标记，命中就静默返回，不调用 debug，不扣预算，不 halt。用例要用真实的取消路径注入。
- **高B：判定与提交在同一回调中可以做到原子，但写法必须明确。** `checkpoint` 经由 `serial`（:1627），回调串行执行。“组已采用？”必须是 commit 回调的第一句，并且在 wizardLineIds、merge、coverage、`w.lineRepairs` 累加（:1045-1050）之前。命中时 `return` 一个哨兵值，不能抛错，否则会被当作失败。组状态要在同一回调里置为已采用。合并失败（LP-15b）不能把组置为已采用。
- **中C：方案第2条第3款会产生混合状态，可能在本可成功时失败。** 一半已提交后，原批次即使成功也要丢弃；另一半如果失败且预算耗尽，步骤就会失败。两半各自继续拆分后，后代也属于这一组，方案没有定义。建议把两半的结果暂存在内存（已校验但不合并），两半都成功时在一个检查点内一起提交。这样组只有“原批次”或“全部两半”两种结局，原批次在两半未全部完成前随时可以被采用。另外规定：第一个后代提交后立即取消原批次。暂停时暂存结果丢弃，恢复后按 coverage 重做，与 3R-7 一致。
- **中D：触发条件。** 名额 ≤31 成立：worker 数固定（:1080），原批次占着自己的 worker，两半只能由空闲 worker 领取。“有空闲名额”只在队列已空的尾部成立，所以不会在中段加重限流，方向正确。问题有两个。第一，LPT 让小批先完成，中位数偏低，此时 30 s 下限实际起主导作用。建议按字数归一化：`耗时 > max(30 s, 2×中位(ms/字)×本批字数)`，成功样本少于 3 个时只用 30 s 下限。第二，单章大批不触发，而尾部慢批正是大批，可以考虑对单章多单元批次按单元切分。
- **中E：预算。** 提前拆分计 2 次额外请求，可能耗尽真实失败所需的预算（3R3 预算 = 初始批数）。建议提前拆分最多使用预算的一半；取消的请求虽然不计入预算，但会写进 E2E 的请求总数。
- **低F：halt、暂停与计时器。** 每个原始批次的计时器在 halt、`current()` 抛 AbortError，以及 runLineParallel 返回时（finally）都要清除。计时器回调里要先检查 halt 和当前 epoch，再入队。原批次失败、两半仍在途时，原批次不扣预算，也不 halt。单元测试应注入时钟，不要用真实的 30 s sleep。

## 结论

**有条件通过。** 进入真实 E2E 前须修复高1（revise 路径清零 lineRepairs），并补中2、中3 的用例。低项可以随实现一并处理。§3R4 的划分算法与调度在正确性上没有问题，也没有引入质量损失。§3R5 实现前须把高A、高B 写进方案，建议采纳中C 的成对暂存提交。120 s 目标仍需真实 E2E 证据。
