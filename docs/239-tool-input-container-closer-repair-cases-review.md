## 四、断言精确性

- **正例断言偏弱**：CL-01～CL-05 目前只断言「parse 成功 + operationSchema 通过 + op 数」。由于 `value` 是 `z.record(z.string(), z.unknown())`，**任意内容都能过 schema**——无法区分「修复正确」与「修复但改动了内容字符」。**建议**：每条正例追加 `assert.deepEqual(解析结果, 期望的完整 ops 数组)`（合成期望值），使「修复但错误」也失败。
- **反例断言**：「入参保持原值」建议明确为 `deepEqual(还原值, 原字符串)`（repairToolInput 层面断言返回 `null`），可三态区分：保持原值=放弃、deepEqual 失败且 parse 成功=修复但错误、两者皆非=修复正确。
- **CL-25**：建议断言「放行 + `ops.length === 1` + `deepEqual(ops[0], 第一条 op 的期望值)`」，区分「放行且正确重建保留 op」与「放行但内容被改」；注释须含方案「范围收窄声明」出处。
- **CL-30a 可实现、无共因盲区**：参照物建议为测试文件内**独立实现的字面量切分器**（逐字符扫描引号/转义、不维护栈、不做补齐），把输入与修正串各自切成「字面量段/结构段」交错序列：断言字面量段逐字节相等、结构段差异仅限闭合符位置。不要用 `JSON.parse` 反推参照（parse 失败时不可用）。与被测栈式扫描器算法不同构，满足「参照物独立」要求。
- **CL-30b 有空洞风险，须补下限断言**：实测其在未修复代码上放行例为 0、断言空过；若不设下限，将来把新逻辑整体删掉它也仍绿。**建议**：（a）语料中固定包含 CL-01/CL-02 型种子的变异，断言「参照实现放行的例子里当前实现放行数 ≥ 下限」或直接断言「放行例数 > 0 且 ≤ 参照实现放行数」；（b）变异后须先 `JSON.parse` 失败才计入语料（合法变异走既有 #8 路径，不能算新逻辑战绩）；（c）拒绝例断言保持原值。
- **CL-30c 第 2 类元缺陷原理上不可杀，须改写**：实测（语料 = CL-01～CL-28 全部夹具）：
  - 元缺陷 1（忘记字面量状态）：**当前语料不可杀**；补 CL-32（字面量含 `}` 的放行例，错误实现会算出 rew=0 而拒绝）后可杀。✅
  - 元缺陷 3（字面量内闭合符计入 rewritten）：**当前语料不可杀**；补 CL-33（rew=0/pad=1 夹具，错误实现会放行）后可杀。✅
  - 元缺陷 2（FIFO 补齐）：**任何输入级语料都不可能杀死**——放行条件要求 `padded ≤ 1`，此时 FIFO 与 LIFO 产出完全相同；差异只在 `padded ≥ 2` 时出现，而该形态必被条件 2 拒绝，行为不可观测。**建议改为**：(a) 把第 2 类错误实现换成可观测的「去掉 `padded ≤ 1` 限制」（会被 CL-18 杀死），或 (b) 保留 FIFO 缺陷但改用函数级断言——要求方案中的 `repairContainerClosers` 以可导入形式暴露（或测试内建同构副本）并对 `padded ≥ 2` 输入直接断言修正串为 LIFO 顺序（`}}]` 而非 `][]`）。当前 CL-30c 写法在实现阶段会得到「FIFO 未被抓住」的假失败，须先修订。
