## 发现

1. **低**：`desktop/core/novel-import-wizard-roster.ts:90`。判定时先看 `parent` 后看 `parallel`。条目同时带 `parallel:true` 和 `parent` 时，会被当作子世界挂到 parent 下。
   - 实测输入：`[{name:'戊界'},{name:'庚界',parallel:true,parent:'戊界'}]`，结果中“庚界”的 `parentId` 为主世界。
   - 契约规定平行世界“不填 parent”，两个字段同时出现是模型的自相矛盾。按定义，平行世界另有一套基础法则，更合理的做法是以 `parallel` 为准、忽略 parent。
   - 建议：把 `e.parallel` 的判断放到 `e.parent` 之前，并补一条用例。

2. **低（需决策）**：`novel-import-wizard-roster.ts:121`。解析不到的 parent 名称被计为投给主世界的票，可能压过明确、可解析的 parent。
   - 实测输入：主世界“戊界”，平行世界“庚界”。子一有 2 批给 parent“庚界”，另 3 批给了 3 个不同且无法解析的名称。结果子一挂到了主世界。
   - 2R-4 写的是“能解析则挂该世界，否则挂主世界”。按逐批理解，当前实现符合字面，但效果是模型编造的名称越多，主世界的票越多。
   - 建议：解析失败的票不计；只有全部票都无法解析时才挂主世界。如果维持现状，在 503 中写明这一取舍。

3. **低**：`novel-import-wizard-roster.ts:78` 与 :132。资料设定的 `settingType` 用 `fixed` 直接覆盖正文的多数票。
   - 以资料文件为准是合理的，但 2R-4 只写了“按出现次数投票”。
   - 缺少对应用例：资料写 FACTION、正文三批写 SOCIETY 时，期望结果为 FACTION。
   - 建议在 503 中补一句说明，并加这条用例。

4. **低**：`main/novel-import.ts:599`。worker 数量在开始时按 `min(15, queue.length)` 固定。
   - 某个 worker 发现队列为空后就退出；之后另一个 worker 的批次失败、拆分重排时，只剩它自己串行处理拆出的子批。
   - 场景识别有 `spawn()` 补充 worker（:661），这里没有。
   - 结果不受影响，只是变慢：第一卷末尾批次被拆分时，可能拖长整步耗时。可以在 E2E 时观察。

5. **低**：`desktop/core/novel-import-wizard.ts:127` 的 `wizardChapterCount` 只按名称和别名在正文中计数。主世界名为“主世界”且原文从未出现这个称呼时，章节数为 0，世界清单上会显示 0 章。
   - 这不影响勾选和导入：世界没有按章节数过滤的规则。
   - 但界面文案应来源于真实状态。建议主世界用 `evidenceUnitIds` 所在章节计数，或者不显示这个数字。

6. **信息**：`novel-import-wizard-roster.ts:114`。子世界名称与主世界相同时，这个条目仍是 sub，其别名会追加到主世界的别名中。这只在正文条目名等于单个资料世界名、且该名不在 `mainNames` 中时发生。别名追加时只过滤 taken，不过滤设定名，与 2R2-1 的“不进入主世界别名”略有出入。影响很小，可以合并到第 1 条一起处理。

7. **信息（范围外）**：`src/lib/ai/tools.ts:2282` 的工具说明举例“灰雾之上的老者”，来自具体作品。它不是导入提示，不在本次 diff 内，但违反用户约束“提示词与通用规则不得出现任何具体小说的设定”。建议另开一项处理，并评估是否需要与上游 Web 同步。
