## 二、新增放行条件 2 的判别力实测（本轮核心）

### 2.1 结论：**不能区分「闭合符错乱」与「真截断」**

方案 235:93-94 的判别依据原文：
> 真实闭合符错乱样本**必然存在类型错位**，即 `rewritten ≥ 1`；真截断只表现为「容器未闭合」，即 `rewritten === 0`。

**后半句在生产语境下为假。** 方案 235:97 的复核（"6 例真截断形态…全部为 `rewritten === 0`"）成立的前提是「从**合法 JSON** 截断」；而生产中进入 `parseEncodedContainer` 的字符串**本身就是供应商已写坏的非法 JSON**（issue #15 根因：内层 JSON 自身闭合符错乱）。非法串再叠加截断，`rewritten` 就不再是 0。

**最小反例（可复现）：**
```
输入： [{"kind":"put","collection":"cards","value":{"id":"c1","title":"标题一","content":"正文一"]}
stats：rewritten=1, dropped=0, padded=1, inString=false
判定： 放行（条件 2 通过）
结果： 解析出 1 个 operation，而模型本意写 2 个 → 静默产出残缺提案
```
该样本经真实 `repairToolInput` + 真实 `operationSchema` 端到端复现：`operations` 长度为 1、`operationSchema.array().safeParse` = true。

**规模化实测**（对含 3 个 operation 的合法文档注入 1 处类型错位后逐字节截断）：放行 19 例，其中 **6 例解析出的 operation 数少于完整文档**。即护栏被绕过的比例不为 0。

**后果与是否有其他护栏接住：**
- 条件 1（字面量完整性）：截断点在字面量之外 → 不触发。
- 条件 3/4（parse 成功、类型一致）：补齐后恰好 parse 成功、类型仍是 array → 均通过。
- 条件 5（内容未变）：修正确实只动了闭合符 → 通过（该条件管的是「改了什么」，管不了「少了什么」）。
- 业务 schema：`operations` 为 `z.array(operationSchema).min(1).max(200)`（`src/lib/planning/domain.ts:236`），1 个元素通过；`value` 为 `z.record(z.string(), z.unknown())`，任意内容合法 → **拦不住**。

**⇒ 与前次 D1 同类的「静默产出残缺提案」风险未被消除，只是从「纯截断」缩小为「截断 + 内容中间已有类型错位」。**

### 2.2 「真截断且 rewritten ≥ 1」样本族（任务要求逐类实测）

| 截断位置 | rewritten | 结果 |
| --- | --- | --- |
| 数字字面量中间（源自合法 JSON） | 0 | 拦截 ✓ |
| 字符串字面量内部 | 0 | 拦截 ✓（条件 1） |
| `true`/`false`/`null` 中间 | 0 | 拦截 ✓ |
| `,` 后 / `:` 后 | 0 | 拦截 ✓ |
| 数组元素中间 / 对象属性中间 / 嵌套中间 | 0 | 拦截 ✓ |
| `\uXXXX` 中间 | 0 | 拦截 ✓（条件 1） |
| 转义反斜杠后 | 0 | 拦截 ✓（条件 1） |
| **类型错位在内容中间 + 后续截断** | **1** | **放行 → 产出残缺提案 ✗** |

（真截断各位置逐字节扫描：合法 JSON 172 个截断点 `rewritten` 恒为 0、放行 0 例 —— 方案 235:97 的结论在「合法 JSON 截断」前提下成立，前提需在方案中写明。）

### 2.3 「真实闭合符错乱但 rewritten === 0」（误拒真实故障）实测

存在，且**不止一例**：

| 形态 | stats | 方案放行条件 2 判定 | 是否真实故障 |
| --- | --- | --- | --- |
| 仅多余闭合符（`dropped=1`） | rew=0, drop=1, pad=0 | **拦截** | 是（issue #15 描述的形态之一） |
| 仅缺失闭合符（`padded≥1`） | rew=0, drop=0, pad=1/2 | **拦截** | 是 |
| 纯类型错位 | rew=1 | 放行 | 是 |

方案 235:92 只写了 `rewritten === 0 && padded > 0` → 放弃，而 235:91 的主条件是 `rewritten ≥ 1 且 padded ≤ 1`。两者**不等价**：按主条件，「纯多余闭合符（rew=0, pad=0, drop=1）」也被放弃；按 92 行的描述则可放行。**实现者会得到不同结果**，方案需收敛为单一表述。

### 2.4 放行条件 2 与 §测量与验收 自相矛盾（阻塞）

- 235:91 放行条件 2 要求 `rewritten ≥ 1`。
- 235:163 验收要求：「真实样本形态的 **3 类缺陷（多余闭合符 / 缺失闭合符 / 类型错位）各有用例**，还原后通过 `operationSchema` 校验」。

实测：3 类中**只有「类型错位」一类能被修复**，另两类均被条件 2 拦下（rew=0）。**验收要求无法同时满足**。235:96 声称真实 5 份样本统计为 `rewritten=2/1/1/2/2`（全部含类型错位）故能过，但「3 类缺陷各有用例并还原成功」与条件 2 不相容。

### 2.5 「中间缺失一律放弃」声明的机制写反了

235:104 称「中间缺失一律放弃（由条件 2 的 `rewritten ≥ 1` 兜住）」。但 `rewritten ≥ 1` 恰恰是**放行**条件，不是拦截条件——它无法「兜住」任何东西。实测：`{"a":{"b":1]`（rew=1, pad=1）→ **放行**，得 `{"a":{"b":1}}`；而 `{"a":{"b":1,"c":2`（rew=0, pad=2）→ 被拦。**同属中间缺失，判定相反**。235:104–106 的声明与 235:91 的条件 2 逻辑不自洽。

## 三、放行条件 5（内容未变）的可实现性与盲区

**可实现性：通过。** 按字面量边界分段（字面量内片段序列 + 字面量外非闭合符骨架）逐字节比对，机械可实现（本次已实现并跑通）。

**盲区：存在共因盲区（D3 未真正闭环）。** 235:112 允许「由修复函数一并返回『字面量内原文片段』供断言使用」。若**比对与修复共用同一个扫描器**，而该扫描器本身有字面量状态缺陷，则两侧同时错、比对仍判「未变」。

实测：故意实现一个「忘记字面量状态」的错误修复器（把字面量内的 `]` 改写成 `}`），原文 `[{"p":"正文里有 ] 符号","q":1}]`：
- 用**同一有缺陷逻辑**做全局剔除闭合符比对 → `true`（漏检，内容已被破坏）
- 用**同一有缺陷逻辑**做分段比对 → 仍 `true`（漏检，共因）
- 用**独立正确扫描器**做分段比对 → `false`（正确检出）

**⇒ 条件 5 必须锚定在独立参照物上**：单元测试用独立于被测实现的参考实现/解析器做交叉比对；或把条件 5 从运行时门禁降级为测试期断言并说明其独立性来源。方案现将条件 5 同时写成「运行时放行条件 5」与「验收断言口径」，定位需明确。

**与 `normalizeToolInput` 既有递归路径的交互：无冲突（通过）。** 实测修复后的容器经 `normalizeToolInput(parsed, matchingContainerSchema(schema, parsed))`（`tool-input-repair.ts:170`）继续规整内部字段正常；`bigFive` 的数字字符串被正确转为数字；数组 items 递归（`tool-input-repair.ts:175`）不受影响；`options`/`targets`（字符串数组）修复后元素仍为字符串。

**附带提醒（既有问题，非本方案引入，但会影响用例断言）：** zod v4 `z.toJSONSchema` 产物偶发出现「`properties` 某 key `hasOwnProperty=false`、直接访问为 `undefined`」（实测出现后，`normalizeToolInput` 的 `properties[key]` 取不到该字段 → 该字段保持原字符串不被规整）。生产 SDK 路径 `asSchema(...).jsonSchema` 实测 300 次均正常。用例文档若用 `z.toJSONSchema` 构造 schema 并断言「5 个维度全部规整为数字」，存在偶发失败风险，建议改用生产同源构造或避免该断言。

## 六、结论与必须先改的内容

**修订后的方案不能直接进入用例设计阶段。** 方向正确、改动面最小、复杂度合格、既有 9 个用例不受影响、前次 9 项修改要求全部落实；但**新增的放行条件 2 不足以承担 D1 的兜底职责**，且**验收要求与放行条件互相矛盾**。按现方案实施，仍可能产出内容残缺且业务 schema 检不出的提案。

进入用例设计阶段前，方案须先落实以下 4 项（均为阻塞或准阻塞）：

1. **修放行条件 2 的判别依据。** 二选一并写死：
   (a) **收窄声明**：明确「真截断 + 内容中间已存在类型错位」形态**不在本次覆盖范围**，把该最小反例写入 235:139-155 反例表，期望 = **不修复**；同时把 235:93-94、235:181 的表述改为不再声称「真截断 → `rewritten === 0`」这一不成立的普适命题。
   (b) **增加第二判别信号**（需在用例阶段验证充分性）：例如要求尾部闭合符连缀具备某种可判定的结构特征，或要求 `padded`/`dropped` 与尾部连缀长度满足某一致条件。本轮已试过两种候选（「改写只落在尾部闭合符区」「内容区单独补齐后自洽」），**均未能拦住最小反例**，故不建议直接采用未经充分验证的规则。
   > 若选 (a)，需同时给出「本次修复只覆盖『尾部闭合符错乱且内容完整』形态」的显式范围声明，并接受「部分真实故障不修复、模型需重试」的既有取舍（与 235:106 的既定取舍一致）。
