# 场景批量导入用量事务修复方案

## 实测后的修订（当前方案）

第二轮实测进一步收窄：UT02的31路真实连接等待均复现P2028；但真实SQL pg_sleep(5.2)使原导入与普通调用都成功，不能证明活动执行超时。故**最终仅设maxWait60000，保留原默认timeout**，不增加30000执行时限。UT07不作为产品修复准入/覆盖或通过成绩；保留该不成立试验的历史。以下30000及UT07是上一轮提议，已被本段取代。

原生数组试验未满足准入：真实连接占用2403ms时仍返回P2028，7项中6通过、1失败；已撤回该产品实现，不能称作GREEN。Prisma数组事务在本地驱动同样受默认启动等待限制。

当前改为保留原交互事务三写，只对下面四个精确导入action显式传递 `{maxWait:60000,timeout:30000}`。启动等待容纳本地单连接批量排队，执行预算容纳完整响应解析与持久化同时进行时的事件循环延迟。两者仍有界；超限继续失败，不重试、吞错或减少模型并发。其它action省略options，保持原默认值。无新队列，不修改适配器或Prisma构造默认值，现有authority/工作区选择与事务原子性原样保留。

沿用真实等待>2秒对照并增加事务内真实SQL延迟>5秒用例，证明启动与执行两种原默认时限均被覆盖。先独审修订方案/用例，再重新RED/GREEN。

## 初始方案与历史依据（已被上节取代）

R18 为诊断运行：951 个候选场景，210 完成、1 失败；捕获 5 次原始 Prisma P2028。正常产物已按 R17 哈希恢复，未发布、未完成验收。R17 独立只读模型请求成功而完整批量失败，因为只读诊断绕过了真实用量写入。

`src/lib/quota.ts` 的 recordActualUsage 使用交互事务，先 upsert 惰性模型引用，再并行插入用量和累加 token。没有依赖前一查询返回值；31 个场景并发和本地单连接队列会触发交互事务等待/执行时限。`src/lib/db.ts` 的 prisma 是请求工作区代理，不是 globalPrisma，必须保留原工作区、写入 authority 和聊天元数据语义。

拟对四种精确导入 action（novel.import.classify/analyze/review/patch）使用 Prisma 原生数组事务，按模型引用、用量插入、计数更新的顺序一次原子提交。该形式适合已知数据的三次写入，避免应用回调交互事务的计时窗口；不更改 PGlite 适配器，不加外层模型重试，不跳过用量错误，不减少模型并发或输入。其他 action 保持当前交互事务行为。仅在真实数据库测试证明批处理不会遇到同一超时后采用；否则返回修订方案审核，不能仅调整测试通过。

保持模型快照校验和成本计算、清除 key 的惰性引用、UsageRecord 的 turn/attempt/novel/action/token 字段、token 原子累加及三次写入的共同回滚。构造 PrismaPromise 必须仍然懒执行并通过同一可信请求 authority，不直接借用底层数据库。

验证顺序：独立方案审核 → 独立用例审核 → 原代码真实数据库 RED → 最小实现 GREEN → 独立代码审核 → 定向回归/类型/构建 → 正常 Electron 全文全场景导入、校验、发布、重启和全字段快照比对。真实导入使用用户已授权的当前 DeepSeek 接口；不运行全仓测试，不输出真实正文/模型原文/Key。
