## P2

### P2-1 最小宽度仍用循环，和修订 1 规定的一步公式不一致

`src/lib/planning/worldline-layout.ts:1742-1756`

修订 1（P2-2 一行）明确改为一步公式：`MIN = min(4, usable / n)`，`width = MIN + (usable − n × MIN) × count / total`。实现保留了“低于 MIN 的段抬到 MIN，其余按比例重分”的循环。

我核对了这个循环：
- 能结束：每轮要么没有新的过窄段而退出，要么至少多固定一段。固定满 n 段时走均分分支退出，所以最多 n + 1 轮。
- 不会出现 NaN：`freeCount > 0` 才做除法；全部固定时用 `usable / n`。
- 宽度总和精确：退出时总和为 `fixed × min + rest = usable`。只在全部固定时走均分分支，总和也等于 `usable`。
- 每段 ≥ MIN：未固定段的宽度在后续轮次只会变大，不会掉回 MIN 以下。

所以循环本身没有错误，结果也比一步公式更接近按比例分配（真实数据中 130 个根事件的段是 99.3px，一步公式下会少几 px）。问题在于它与已批准的修订 1 不一致，且方案和台账都没有记录这次偏离。按 AGENTS.md，方案是验收依据。需要二选一：在方案里补一条“修订 2：保留循环”，写明理由和上述结束与总和的论证；或者改成一步公式。另外，均分分支（`fixed.size === n`）没有用例能确定覆盖到。MM-03 的 W = 30 是否进入这个分支取决于数据，用例本身没有断言。

### P2-2 点击窄段时，视窗常常跳不到该段（调用方遗留问题，修复后仍存在）

`src/components/content/planning/worldline/EventTimeline.tsx:482-485`、`:801-806`

点击视窗框外时，`miniDrag.offset` 取当前框像素宽度的一半，`moveMini` 用 `left = px − offset` 再 `toT(left)`。缩略图按段分段，不是线性的：框的像素宽度在不同位置差别很大，而现在大多数段只有 4px。只要半个框宽超过半个段宽，`left` 就会落到前一段或间距里，视窗开始时间变成前一段的时间，被点的段可能完全不在视窗内。

我用真实数据在 420px 下做了模拟（脚本已删除）：视窗先停在段 j 的中心，再点击段 k 的中心，统计被点段的根事件进入视窗的比例。共 30 × 29 = 870 组。

| 视窗跨度 | 新代码未命中 | 其中半框宽 > 半段宽 | HEAD 未命中 |
|---|---|---|---|
| 2 年 | 233 | 186 | 351 |
| 10 年 | 198 | 198 | 141 |
| 50 年 | 111 | 111 | 89 |

这不是 `minimapModel` 的错误，也不在本次 diff 内。但方案的真实目标验收要求“点击三个段中心后视窗内出现该段的事件”。如果选到 4px 的单事件段，这条验收会失败。MM-B1 点击的是第 5、17、28 段（16、20、17 个根事件），都是宽段，并且先把视窗缩到 ≤ 1500 年，所以覆盖不到这个情况。建议主代理决定：要么在真实目标验收中明确只选宽段并记录这个限制；要么另开一项，把框外点击改成按时间居中（例如 `start = toT(px) − span / 2`），并补一个“点击 4px 单事件段”的浏览器用例。

## P3

### P3-1 段时间范围不再包含家族结束，长家族尾部的视窗框贴在段边

`src/lib/planning/worldline-layout.ts:1761-1762`

这是修订 1 P2-1 有意的取舍。后果是：视窗停在一个长家族的后半段（那里没有根事件开始）时，`toX` 把两端都夹到该段 `t1`，框缩成 `Math.max(8, …)` 的最小宽度，贴在段右边（`EventTimeline.tsx:551`、`:824`）。这和视窗落在段间空档时的现有表现一样，可以接受，但方案里最好写一句。

### P3-2 `aria-valuemin/max` 含义与修订 1 一致

`EventTimeline.tsx:795-796` 仍取首段 `t0`、末段 `t1`。首段 `t0` 仍为 `a − pad`，末段 `t1` 现在不含家族结束，比修复前小。`aria-valuenow` 超出这个范围的情况比以前多一些，修订 1 已决定不改。这里只做记录。

### P3-3 用例小问题

- `tests/unit/worldline-layout.test.ts`，`mmCheck` 的 `roots` 参数没有用到，只写了 `void roots`。可以删除这个参数。
- `mmSegments` 的 `extra` 默认值写成 `{} as any`，又用 `typeof extra === 'function'` 判断，类型声明和实际用法不一致。可以改成默认 `() => ({})`。
- MM-03 没有专门构造“浮点误差导致最后一段也被固定”的情况（修订 1 P2-2 的场景），只断言宽度是有限值、总和为 W。见 P2-1。

## 逐项核对（无问题）

- 间距：`gap = min(14, 0.2W / (n − 1))`，n ≤ 1 时为 0，总和 ≤ 0.2W（1740 行）。2 段且 W = 420 时仍为 14px，WU-20 不受影响。
- 段范围：`t0 = max(a − pad, (前段 z + a) / 2)`，`t1 = min(z + pad, (z + 后段 a) / 2)`，用的是 `railSegments` 的原始 `t1`（最后一个根事件开始），所以相邻段 `t1 ≤ 后段 t0`。段之间至少隔 `breakHours`（≥ 30 天），中点离段边远大于 `dayHours`，同一时间的段也有 `2 × dayHours` 的宽度，不会除零。
- `toX`：取最后一个 `t0 ≤ t` 的段并夹到 [0, 1]。早于首段时夹到 0，晚于末段时夹到 W，空档内夹到前段右边。单调。
- `toT`：按 `x0 + width + gap / 2` 找段，左半个间距映射到前段 `t1`，右半个映射到后段 `t0`。单调，且在段内与 `toX` 互逆（MM-01 抽样 2000 点验证）。
- 0 个根事件：`toX`、`toT` 返回 0，没有段。W = 0 时 `min = 0`、宽度为 0，不会出现 NaN。调用方 `miniWidth` 最小为 4（`width > 0`），不会出现负宽度。
- MM-B1：标记按 `tree.roots` 顺序检查是否落在自己的段框内，在 1440 和 820 两种宽度下运行；拖动用例把框左边拖到第 12 段起点，`toT(x0) = 段 t0`，断言合理。
