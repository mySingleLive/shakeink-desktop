## 一、独立审核门禁逐条结论

### 门禁 1：是否严格只增删改闭合符，是否存在内容字符被改动的路径 —— **通过（算法本身）／验收断言口径需修改**

- 算法本体：按方案描述实现后，扫描只对 `}` `]` 做改写/丢弃/补齐，其余字符（含字面量内容）原样进入输出。随机变异 39 218 例（闭合符替换类型/删除/插入），修复成功 20 776 例，**内容字符改动 0 例**；修复后与原意图语义一致 20 776/20 776。
- 但方案第 116 行提出的断言口径「剔除所有闭合符后，修复前后字符串完全相同」**有盲区**：它无法发现「字面量内部的闭合符被改写」。实证：一个忘记字面量状态的错误实现把字面量内 `]` 改写成 `}`，`剔除闭合符后相同 = true`，而正文已由「正文里有 ] 符号」被改成「正文里有 } 符号」，而 `JSON.parse` 仍成功。
- 建议：放行条件 3 的实现与断言必须改为「**按字面量边界切分后，逐段字节比对**」或「**剔除闭合符时保留字面量内闭合符**」，不能只做全局 `replace(/[{}\[\]]/g,"")`。

### 门禁 2：「字符串字面量未闭合 → 放弃修复」护栏是否在所有分支生效 —— **不通过**

- 护栏本身在方案原样实现下有效：字面量未闭合时返回 `undefined`（截断在字符串字面量内部的输入被正确拒绝）。但**该护栏只覆盖「截断点落在字面量内部」这一种截断位置**，方案第 104/110 行把它当成「内容真被截断」的**通用**判据，这是错的。
- 实测截断点落在字面量之外时护栏全部失效：
  | 截断位置 | 方案护栏 | 实测结果 |
  | --- | --- | --- |
  | 数字字面量中间 `{"count":123`（原意 12345） | 未触发 | **修复成功**，值被静默改为 123 |
  | 数组元素内容缺失（字面量已闭合） | 未触发 | **修复成功**，元素数看似正常但内容残缺 |
  | 尾部少 `]` / 少 `}` | 未触发 | **修复成功** |
  | `true`/`false`/`null` 关键字中间 `tru`/`fals` | 未触发 | 靠 `JSON.parse` 恰好失败而放弃（**偶然**，非护栏） |
  | `,` 之后 / `:` 之后 | 未触发 | 靠 `JSON.parse` 失败而放弃（偶然） |
- 关键实证：逐字节截断 282 个位置统计 → 放弃 254（字面量未闭合 204 + parse 失败 50）、**修复成功 28，其中 25 例内容静默缺失、仅 3 例与完整内容一致**。
- 结论：护栏只挡住 1/4 级别的截断位置，其余靠 `JSON.parse` 偶然失败。方案「真截断 → 不修复」的整体承诺不成立。

### 门禁 3：三条放行条件是否都在最终放行前被检查 —— **需修改**

- 方案第 81–85 行三条条件齐全，但**放行条件 2 与 3 的判定口径未定义到可实现程度**：
  - 条件 2「容器类型与 schema 声明的类型一致」：当 schema 同时允许 `object` 与 `array`（`anyOf`/`oneOf` 分支）时无唯一判定；既有 `parseEncodedContainer`（`tool-input-repair.ts:160-161`）的既有口径是「按 parsed 的实际类型二选一命中」，方案应明确沿用 `matchingContainerSchema` 既有口径而非另立一套。
  - 条件 3 的实现方式如门禁 1 所述有盲区。
- 另：**方案未定义「放行条件的求值顺序」**。正确顺序必须是「先扫描 → 统计改写/丢弃/补齐 → 字面量未闭合则放弃 → parse → 类型一致 → 内容未变 → 放行」。方案第 110 行把「字面量未闭合」放在「边界与反例」一节而不在「处理」步骤里（第 69–79 行），实现者可能先补齐再判护栏。

### 门禁 4：扫描是否对超长输入为线性复杂度 —— **通过**

- 实测（同一算法，数组栈 + 输出数组 + join）：

  | 输入长度 | 耗时 | 每万字符 |
  | --- | --- | --- |
  | 1 340 001 | 44.8 ms | 0.33 ms |
  | 2 680 001 | 86.1 ms | 0.32 ms |
  | 5 360 001 | 179.8 ms | 0.34 ms |
  | 10 720 001 | 371.1 ms | 0.35 ms |

  每万字符耗时恒定 → 确认 O(n)。2.9 MB 输入单次扫描 92.8 ms，可接受。
- 实现约束（须写入方案）：输出必须用**数组 push + 末尾 join**；若用字符串 `+=` 拼接，在 V8 上虽仍是摊还 O(n)，但会显著抬高内存峰值，建议明文要求。

### 门禁 5：是否与既有 `parseEncodedContainer` 三条前置判据、`parsePlanningToolJson` 路径冲突或重复修复 —— **通过**

- 用方案原样实现打补丁（临时副本）跑真实 `repairToolInput`：
  - 合法字符串化对象 → 还原；普通字符串字段 → 不动；无效 JSON → 不动；类型不匹配 → 不动；联合含 string → 不动。既有 9 个单测**全部通过**（补丁版副本 `tests 9 / pass 9 / fail 0`），仓库原版同样 `pass 9 / fail 0`。
- 三条前置判据（`tool-input-repair.ts:152-157`）在新逻辑之前生效，实测逐条复现：schema 未声明容器 → 跳过；联合含 string → 跳过；不以 `{`/`[` 开头 → 跳过。新逻辑只挂在 `JSON.parse` 失败的 catch 分支上，**不与既有合法 JSON 路径重复修复**。
- 与 `parsePlanningToolJson` 无冲突：前者处理顶层 tool call JSON（含 `repairPlanningClosingBoundary`），后者处理内层被字符串化的容器，两者作用层级不同；实测补丁版对 `proposeNovelPlanning` 走真实路径可正确还原出数组并通过 `operationSchema` 校验。
- 唯一需注意点：`normalizeToolInput` 的递归（`tool-input-repair.ts:175`）会对数组元素逐项调用 `normalizeToolInput`，**不会**再次进入 `parseEncodedContainer` 的字符串分支（元素已是对象/数组），无重复修复风险。

### 门禁 6：反例是否覆盖充分 —— **不通过**

方案第 101–108 行的反例表覆盖了「字面量内截断、类型不符、普通字符串、联合类型、不以括号开头」，但**恰恰漏掉了最危险的一类**：

- 缺失：**截断点落在字面量之外**（数字字面量中间、尾部少闭合符、元素内容在字面量内已闭合但后续缺失）。方案把它归入「内容真被截断 → 不修复」，但实现上拦不住（第 2 条门禁已证）。
- 缺失：**「中间缺一个闭合符」与「尾部缺一个闭合符」的歧义**。同一串字节 `{"a":{"b":1,"c":2` 可对应两种意图：`{"a":{"b":1,"c":2}}`（尾部缺）或 `{"a":{"b":1},"c":2}`（中间缺）。方案算法**只能补在尾部**，无法消歧；实测真实 operations 形态的「中间缺 `}`」版本，修复结果 `parse` 失败 → 放弃（幸运），但 `{"a":{"b":1,"c":2` 这类会补成 `{"a":{"b":1,"c":2}}`，与意图 B 不符且**无法被任何护栏识别**。
- 缺失：**方案第 104 行表格里的「尾部缺内容、字符串未闭合」被合并成一行**，但两者需要完全不同的护栏。

### 门禁 7：是否未改动 `toolInputIssueHint`、`normalizeToolInput` 其他分支、schema 定义或业务逻辑 —— **通过**

- 方案第 97 行声明 `toolInputIssueHint` 不改，实测补丁版 `toolInputIssueHint` 行为与原版完全一致（错误提示仍区分「缺少 X」与「X: 应为对象，实际为字符串」）。
- `normalizeToolInput`（`tool-input-repair.ts:167-187`）的其他分支（number/boolean 转换、数组 items 递归、对象 properties 递归、null 剔除）均未触及。
- schema 定义（`src/lib/planning/domain.ts:236` 的 `operationSchema`、`src/lib/ai/planning-tools.ts:65`）与业务逻辑未变；补丁版 diff 仅新增 `repairContainerClosers` 函数 + `parseEncodedContainer` 的 catch 分支。
- 方案第 91 行称「覆盖 `updateCharacter.bigFive`、`upsertAttribute.options`/`targets`」——`upsertAttribute` 确在 `src/lib/ai/tools.ts:1290` 存在；但 **`updateCharacter.bigFive` 的 schema 是对象且可空**，其顶层 `types` 集合为 `{object, null}`，不含 `string`，新逻辑可命中；此路径与 issue #15 的 `proposeNovelPlanning` 无关，属扩展范围，**方案应明确本次是否要覆盖**（见下）。

## 二、方案缺陷清单（按严重度）

### D1【严重】真截断被误判为「修复成功」，产出内容残缺的提案且业务 schema 拦不住

方案把「字面量未闭合」当作真截断的通用判据（104/110 行），实际只覆盖 1/4 的截断位置。实证（用方案原样实现 + 真实 `repairToolInput` + 真实 `operationSchema`）：

```
输入 operations: [{"kind":"put","collection":"cards","value":{"id":"card_1","title":"第一张卡片"}},
                  {"kind":"put","collection":"cards","value":{"id":"card_2"
→ repairToolInput 返回修复结果（不是 null）
→ 修复后: [...,{"kind":"put","collection":"cards","value":{"id":"card_2"}}]
→ 元素数 2（看似正确），但第 2 个 operation 的 title 被凭空补成缺失
→ operationSchema 校验：全部通过（value 是 z.record(z.string(), z.unknown())，任意内容都合法）
→ 业务层不会报错，残缺提案会被当合法提案落库
```

数字字面量截断同理：`{"count":123`（原意 12345）→ 修复成 `{"count":123}`，**数值被静默改变**，`operationSchema` 通过。

这直接违反方案第 96 行「内容缺失（真截断）时无法靠闭合符修复，会自然失败并放弃」和第 132 行「字符串字面量未闭合时放弃修复（硬护栏）」的风险缓解承诺——该缓解**不成立**。

**修复建议（精确到函数行为）**：在 `repairContainerClosers` 中引入**判别信号**，并作为新的放行条件：

- 记录 `rewritten`（类型改写数）、`dropped`（丢弃数）、`padded`（补齐数）。
- 新增放行条件 4：**`rewritten === 0 && padded > 0` → 放弃修复**。
  依据：真实闭合符错乱的样本**必然存在类型错位**，即 `rewritten ≥ 1`（方案第 35–39 行的 5 份真实样本统计里，「改写」列分别为 2/1/1/2/2，**无一为 0**）；而纯截断（尾部被切断）只会表现为「容器未闭合」，即 `rewritten === 0`。
- 实证有效性（verify11，8 例）：该条件对 2 例真实形态样本**全部放行且修复结果与原意图一致**；对 6 例真截断样本**全部拦截**；误拒真实样本 0 例、误纳真截断 0 例。
- 补充说明：仅靠 `rewritten === 0` 会误拒「模型只漏写尾部闭合符、其余全对」这一变体（方案真实样本里 2231/2130 两例是「尾部缺 1 个 + 1 处类型错位」，仍含 rewritten=1，不受影响）。若主代理希望覆盖 rewritten=0 且仅尾部缺闭合符的变体，需另立判据（例如「尾部最后一个非闭合符字符是一个完整的字符串字面量或完整数字，且其后的内容不含 `,`/`:` 悬挂」），但这会与数字截断再次冲突，建议本次**不做**，先以保守护栏落地。

### D2【严重】「中间缺闭合符」与「尾部缺闭合符」不可消歧，方案无任何识别规则

方案第 77 行「按栈底到栈顶补齐」只会在**尾部**补，无法识别中间缺失。同一字节串 `{"a":{"b":1,"c":2` 补出 `{"a":{"b":1,"c":2}}`（意图 A 尾部缺），而若模型本意是 `{"a":{"b":1},"c":2}`（意图 B 中间缺），修复结果与本意**结构不同**（`c` 从顶层被吸入 `a`）。方案第 96 行「不臆造内容」只约束了字符级，未约束结构级。

**修复建议**：
- 在方案中显式承认该歧义存在，并声明**本次修复只覆盖「尾部缺闭合符 + 至少一处类型错位」的形态**；中间缺失一律放弃。
- 落地方式即 D1 的条件 4：`rewritten === 0 && padded > 0` 放弃；同时补充约束——**仅当补齐后 `padded` 层数与末尾残留栈深一致，且原始串最后一个容器上下文无歧义时才放行**。更保守且更易实现的做法：把放行条件收紧为「`rewritten ≥ 1` **且** `padded ≤ 1`」，把「多层补齐」直接判为歧义放弃（真实样本最多补 1 层，见方案第 35–39 行「补齐 1 处」）。
- 单元用例须加入「中间缺 `}`」形态，期望结果为**放弃修复**。

### D3【中】方案的验收断言口径有盲区（见门禁 1）

`剔除所有闭合符后，修复前后字符串完全相同`（第 116 行）无法发现字面量内容被改。必须改为按字面量边界切分后逐段比对，或在剔除时保留字面量内的闭合符。

### D4【中】补齐顺序的方案文字有歧义，按字面读法会产生非法 JSON

方案第 77 行写「按栈底到栈顶补齐」。字面实现（先补栈底）产出 `..."title":"标题"}]}` → **parse 失败**；必须按栈顶→栈底（LIFO）弹出才能产出 `..."title":"标题"}}]`。实测（verify12，缺 2/3 层两种用例）两种顺序结果不同且仅 LIFO 可解析。方案文字须改为「按栈顶→栈底（后进先出）顺序补齐」。

### D5【中】转义处理措辞不足以保证实现正确

方案第 71 行写「只识别 `\"` 转义与闭合 `"`」。若按字面实现（仅 `\"` 算转义），遇到 JSON 中合法的 `\\`（转义反斜杠）结尾的字符串会**误判为字面量未闭合**而放弃修复：`[{"p":"C:\\"}]` → quoteOnly 口径「放弃（字面量未闭合）」，generic 口径「修复成功」。既有 `repairPlanningClosingBoundary`（`tool-input-repair.ts:14-23`）用的是通用 `escaped` 标志，方案必须写明沿用同一口径（任意 `\` 后的字符均被消费），并把 `\uXXXX` 纳入用例（`\u` 只消费 `\` 与 `u` 两字符，其余 4 位十六进制按普通字符处理即可，当前实现正确）。

### D6【轻】放行条件 2 的「类型一致」在 object/array 联合下无唯一判定

需明确沿用既有 `matchingContainerSchema`（`tool-input-repair.ts:134-148`）的既有口径，避免两套标准。

### D7【轻】方案引用的前置文档不存在

方案第 5 行引用 `[调研与根因定位](234-placeholder.md)`；`docs/` 下实际只有 `234-sidebar-help-menu-summary.md`，**`234-placeholder.md` 不存在**（实测 `Test-Path docs\234-placeholder.md` → False）。根因事实无法从仓库内追溯，需补齐或修正引用。

### D8【轻】范围表述需澄清

方案第 91 行称本修复覆盖 `updateCharacter.bigFive`、`upsertAttribute.options`/`targets`。`upsertAttribute` 确在 `src/lib/ai/tools.ts:1290` 存在，但这些工具与 issue #15 的 `proposeNovelPlanning` 无关，且其 schema 结构不同（`bigFive` 是可空对象）。方案应明确：本次是**通用容器路径修复**（同一函数自然覆盖全部工具），还是**仅针对 proposeNovelPlanning**。若为通用修复，须补充这些工具的回归用例，否则属于未声明的影响面扩大。

## 三、方案核心疑点的独立验证结论（逐条回答）

| 疑点 | 结论 | 依据 |
| --- | --- | --- |
| 栈顶是 `{` 而遇到 `]` 时，改写为 `}` 是否总是正确？ | **在「模型只是把闭合符类型写反」的前提下正确**（`{"a":[1,2}`→`{"a":[1,2]}`、`{"a":{"b":1]`→`{"a":{"b":1}}`、`[{"a":1]`→`[{"a":1}]` 均与意图一致）。**但该规则无法区分「类型写反」与「漏写开括号」**：`{"a":1]`（意图 `{"a":[1]}`）会被改写为 `{"a":1}`，数组结构静默丢失，且无任何护栏可识别。方案需声明该规则的适用范围。 |
| 栈为空时丢弃多余闭合符，是否可能丢掉语义上必要的闭合符？ | **在「多余闭合符位于尾部」时安全**（`{"a":1}}`、`{"a":1]}`、`{"a":1}]}` 均正确）。**当多余闭合符之后还有内容时会错位**：`{"a":1}},"b":2}` → 丢弃 2 个后得到 `{"a":1},"b":2`，parse 失败被拦下（安全但不可修复）。未发现「丢弃导致内容被静默改变且仍 parse 成功」的情形。 |
| 扫描结束仍有余留时补齐闭合符，会不会伪造出「结构完整但内容残缺」的容器？ | **会，且这是本方案最严重的缺陷。** 补齐只发生在尾部，无法识别中间缺失；更严重的是，若输入本身是被截断的，补齐会把它补成一个「看起来完整」的容器。实测 `{"count":123`（原意 12345）→ `{"count":123}`（数值被静默改变）；`[...{"value":{"id":"c2"` → 补成 `[...,{"value":{"id":"c2"}}]`（内容残缺但 `operationSchema` 通过）。**方案的「字面量未闭合则放弃」护栏拦不住这两类**，必须增加 D1 的判别信号。 |
| 截断在 `}` 与 `,` 之间 / 数字字面量中间 / `true`/`false` 关键字中间，护栏是否失效？ | `}` 与 `,` 之间（如 `[...,{"a":1},`）→ parse 失败被拦下（安全，偶然）。**数字字面量中间 → 护栏完全失效，被误判为修复成功，数值被静默改变**。`true`/`false`/`null` 关键字中间 → parse 失败被拦下（安全，偶然）。`:` 之后 → 同上（偶然）。**结论：护栏仅在字面量内部有效，其余靠 `JSON.parse` 偶然失败，不能作为设计依据。** |
| 数值字面量、布尔字面量、null、转义序列在扫描中的处理是否完备？ | 数值/布尔/null 在扫描中只是普通字符，不会被误当作结构符号，**处理完备**（`{"n":-1.5e+10}`、`{"a":true,"b":false,"c":null}` 均正确）。转义序列：需按**通用 escaped 标志**实现（消费 `\` 后的任意字符），否则 `\\` 结尾的合法 JSON 会被误判为未闭合（见 D5）。`\uXXXX` 当前实现正确。 |
