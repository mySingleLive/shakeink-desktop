## P0：实现前必须处理

### 1. 折叠的父卡宽度是整个家族的时间跨度，并非“只算自身”；层叠卡下还会画轨道

方案 §3 写道：“宽度回到 `widthOf(n) × c`（不再是家族宽度——折叠时 `extent` 只算自身，已有）”。代码并非如此：

- `extent()`（`worldline-layout.ts:1241-1246`）只有 `!n.children.length` 时返回自身宽度；有子事件的节点即使折叠，也返回 `max(wx(start) + PARENT_BAR_MIN_WIDTH, wx(familyEnd(n)), own)`，`familyEnd` 包括全部子孙（`:514-520`）。`visibleKids` 为空只去掉了子卡那一项。
- `layout()` 的父事件分支（`:1266-1268`）对折叠的父卡同样执行 `width = extent(n) - left`，并且总是推入 `track`（`top + height - 3`）。

失败情形：放大到 d ≈ 400px（级别 0）后手动折叠一个持续两个月的家族。层叠卡的宽度是两个月的像素长度（约 700px），不是设计稿中按标题估算的宽度。家族盒的 `right` 也随之变宽，挤占横向空间。轨道会画在层叠卡底部往上 3px，正好落在下方露出的两层底卡上。设计稿只在 `kids.length && !folded` 时加宽（`index.html:327-336`），也只在不折叠时画轨道（`:341`）。

建议：`extent()` 与 `layout()` 对“有子事件但 `visibleKids` 为空”的节点按叶子处理：宽度为 `widthOf(n) × c`，不推入 `track`（持续时间条 `bar` 是否保留需要说明，设计稿没有画）。单元测试 ZP-12 增加一条：折叠家族的卡宽等于 `widthOf × c`、没有 `track` 片段。WU 现有用例中断言折叠父卡宽度的需复查。

### 2. 自动折叠时点折叠钮，方案没有定义去向，现有路径会改写 `foldedEvents`

方案 §2.2 写“自动折叠只影响时间线……不写入 `foldedEvents`”，§2.3 用 `unfolded` 记录用户例外，ZB-05 期望“点父卡折叠钮展开该家族，其他仍折叠”。但时间线卡片的折叠钮直接调用 `onFold`（`EventCard.tsx:173`，`EventTimeline.tsx:612`），而 `onFold` 是 PlanningWorkspace 的 `setFoldedEvents` 切换（`PlanningWorkspace.tsx:2864`）。

失败情形：

- 级别 3 下，一个自动折叠的家族 A 不在 `foldedEvents` 中。用户点它的折叠钮，`onFold(A)` 把 A **加入** `foldedEvents`。时间线上 A 仍然折叠（并集），点击看似无效；事件表与事件目录中的 A 却被折叠了，违反 C1 和 §2.2。
- A 已被用户手动折叠（在 `foldedEvents` 中）。级别 3 下点折叠钮，`onFold` 把它从 `foldedEvents` 移除，但 `autoFolded` 仍包含 A，时间线上没有变化。
- 折叠钮的 `aria-label`、`aria-expanded` 由 `p.folded` 决定（`EventCard.tsx:171-172`），方案需要明确时间线传入的是并集。

建议：`EventTimeline` 包一层折叠处理。`id ∈ autoFolded` 时加入 `unfolded`，不调用 `onFold`；`id ∈ unfolded` 且级别 ≥ 3 时从 `unfolded` 移除；只有不在自动折叠范围内时才调用 `onFold`。`foldedEvents` 中的家族在级别 ≥ 3 时是否允许通过 `unfolded` 展开，需要写明（建议：`unfolded` 优先，并集改为 `(foldedEvents ∪ autoFolded) − unfolded`）。补充用例：级别 3 下点自动折叠家族的折叠钮，事件表 `[data-fold]` 的 `aria-expanded` 不变、`foldedEvents` 不变；再点一次恢复折叠。

### 3. 画布上只有时间点时，“视图内没有事件”浮层误报，首次居中永远不执行

`EventTimeline` 中两处只认 `kind === "card"`：

- 首次打开居中（`EventTimeline.tsx:406-424`）：`cards = step.elements.filter((e) => e.kind === "card")`，为空时保留居中请求并返回。
- 空视图判定（`:426-430`）：视窗内没有 `card` 元素就显示“视图内没有事件 · 复位”。

失败情形：一条世界线没有“关键”事件（或图例筛选隐藏了“关键”，docs/591），复位窗口落在级别 4（真实数据的复位窗口 d ≈ 0.2px，见调研“真实数据模拟”）。所有事件都画成时间点：浮层盖在时间点上提示“视图内没有事件”，首次居中不执行，`takeCenterRequest` 一直挂着，直到某次出现卡片时突然移动画布。级别 2–3 下视窗内只有“一般”事件时也会出现同样的情形。

建议：两处都把 `kind === "point"` 计入。方案 §2.5 列出所有按 `kind === "card"` 过滤的地方（还有框选 `:558`、视窗外保留渲染 `:572`），逐一说明。补充用例：只有“一般/重要”事件的合成世界线，级别 4 打开时无 `[data-empty-view]`，时间点在视窗内居中。

### 4. `-webkit-line-clamp` 会在第二行末尾画省略号

方案 §1.3 的 `.title` 用 `display: -webkit-box; -webkit-line-clamp: 2`，同时要求“不出现省略号（WU-35 保持）”。Chromium 中 `-webkit-line-clamp` 截断时本身就会在最后一行末尾画“…”，与 `text-overflow` 无关。WU-35 与 ZB-01 只检查计算样式 `text-overflow`（`planning-worldline-table.test.ts:114`），所以会通过，但界面上仍有省略号。设计稿用的也是这套 CSS（`index.html:38`），批准的要求是“渐隐，不用省略号”（调研 R3″，方案 §1.3）。

失败情形：真实数据中有 2 个标题两行放不下（调研“标题长度”表），窄面板事件表中有 8 个。这些卡片第二行末尾出现“…”，再叠一层渐隐遮罩。

建议：不用 `-webkit-box`，改为 `white-space: normal; max-height: 36px; overflow: hidden`。截断判定仍用 `scrollHeight > clientHeight + 1`，遮罩不变。补充一个能看出省略号的断言：例如在 `.title` 上用 `Range.getClientRects()` 取最后一个可见字符，确认它是原标题中的字符；或者截图人工核对，并在证据中注明。

## P1：应在方案中写明

### 5. 事件表的宽度公式与 CSS 不一致，行数估算会出错

方案 §1.2 设 `slotWidth = min(880, cardsWidth − 12 − 24)`，子卡上限 `slotWidth − depth × TABLE_INDENT`，分组标题卡宽 `min(slotWidth + 36, 940) − depth × TABLE_INDENT`。CSS 中：

- 窄面板（≤ 640px）`.cards` 右内边距与 `.slot`、`.groupBox` 的 `right` 都是 10px（`worldline.module.css:332-333`），不是 24px。
- 分组框本身是 `left: 12px; right: 24px; max-width: 940px`（`:209`），组内的 `.slot` 再相对分组框取 `left: 12px; right: 24px`（`:204`），外加 `marginLeft = c.left − g.left`（`EventTable.tsx:147`，`renderLevel` `:430`）。每嵌套一层宽度少 36px（窄面板 22px），并非只少 `TABLE_INDENT`。
- 分组标题卡宽 = 分组框宽 = `min(940, cardsWidth − 36)`。方案的 `min(slotWidth + 36, 940)` 等于 `min(cardsWidth, 916)`，比实际宽 36px。

数值例：面板 470px 时 `.cards` 的 `clientWidth` 约 350px。实际一级子卡上限 = (350 − 22) − 22 − 18 = 288px，方案算出 (350 − 22) − 18 = 310px，差 22px，约 1.7 个汉字。调研中窄面板 679 张两行卡里，处在这个边界内的卡会估成 1 行而 DOM 是 2 行，下方卡片被压住，直到测量修正后才跳开。

建议：宽度按 CSS 的嵌套规则逐层推导（窄面板与宽面板用不同的边距常量，与 `narrow` 判定一致），或者直接测量每个分组框的宽度。ZB-02 补充窄面板中嵌套一级子卡和分组标题卡的两行情形，断言估算高度 = DOM 高度（不能只靠测量兜底）。表格头像是 18px（`:126`），时间线是 16px（`:131`），`collapsedHeadChrome` 要按视图区分。

### 6. 分组标题卡的头部高度是固定的 36px，两行标题放不下，中线也会偏

现有 `.groupHead .head { height: 36px }`（`worldline.module.css:219`）。方案 §1.3 把 `.head` 改为 `height: auto; padding: 7px …; align-items: flex-start`，但没有提到 `.groupHead`。按方案的 CSS：

- 固定的 36px 仍然生效，两行标题的分组标题卡第二行被裁掉，`tableLayout` 却给了 54px。
- 标题卡没有边框（`:215` `border: 0`），第一行中线在 7 + 9 = 16px，而 `cardHeadOffset(true, false)` 仍是 18（`worldline-layout.ts:637`）。对齐模式下圆点与引线比标题低 2px。RM-B5（`planning-worldline-table-rail-modes.test.ts:193-204`）断言标题卡高 36，单行时由固定高度保证，看不出中线偏移。

建议：`.groupHead .head` 改为 `height: auto; padding-block: 9px`（0 + 9 + 18 + 9 = 36），两行时 54；`GROUP_HEAD_HEIGHT + (lines − 1) × 18`。ZB-02 增加分组标题卡两行时的高度和中线断言。

### 7. 收起卡测量会让平移触发重排，测量值也可能用错系数

方案 §1.2 让收起卡也进入 `heights`，“只在估算为 2 行或 DOM 实际高度 ≠ 估算时写入”。

- 要知道“DOM ≠ 估算”，必须观察所有收起卡。时间线目前只观察展开卡（`EventTimeline.tsx:249-255`），并按 `vband` 剔除视窗外的卡片（`:571-573`）。平移时新进入 `vband` 的卡片挂载后，ResizeObserver 报告一次，凡是不一致的卡片都会写 `heights`，`heights` 是 relayout 的输入（`:173`），于是平移触发增量重排，卡片在拖动中移位。这违反组件注释中“panning only moves the plane and never re-lays out”（`:80-82`）。
- 方案 §7.2 说测量值除以 `c` 后存原尺寸。ResizeObserver 回调与缩放帧不同步：回调里拿到的是旧系数下的 `getBoundingClientRect()`（`:234`），如果除以当前的 `c`，存进去的值就错了。
- 事件表的测量 effect 依赖 `layout`（`EventTable.tsx:215`），每次布局变化都重新观察所有 `[data-measure-id]`。收起卡都带上测量 id 后，每次折叠、缩放都要重新观察几百个元素。

失败情形：前文的估算误差（第 5 条）或字体回退产生 1 行与 2 行的差异，用户平移时卡片被推开；滚轮连续缩放时，`c` 从 0.9 变到 0.85，回调按 0.85 去除 0.9 下量到的高度，得到 52 × 0.9 / 0.85 ≈ 55，下一帧重排把卡片下推 3px。

建议：测量时从元素自身读取它渲染时用的系数（例如 `data-card-zoom` 属性），再换算；只在暂停交互后（指针抬起、缩放结束一帧后）批量提交收起卡的测量；方案写明平移帧中 relayout 仍为 false，并加用例：两行估算故意错一张卡（用一个估算不准的字符），平移 30 帧期间 `packMode` 为 null。

### 8. 点击时间点后，键盘操作失效；双击编辑不稳定

- `EventPoint` 设 `role="button" tabIndex={-1}`。画布的 `onPointerDown` 只在 `!typing(e.target)` 时把焦点交给时间线（`EventTimeline.tsx:534`），而 `typing()` 把 `[role=button]` 当作控件（`:720`）。`tabIndex=-1` 的元素被点击后自己获得焦点，下一帧它变回卡片、被卸载，焦点落到 `body`。之后 Delete、方向键、空格平移都由时间线根节点的 `onKeyDown` 处理（`:444-464`），全部失效。失败情形：点击时间点选中，按 Delete，没有反应。
- 第一次单击后时间点变卡片，`points` 集合身份改变，触发增量重排。卡片比时间点宽，家族内的行分配（`worldline-layout.ts:1273-1278`）可能变化，子事件换到另一行。第二次点击落在空白处，走 `onClearSelection`（`:561`），选中被清掉，事件又变回时间点。ZB-09 只测根事件的时间点（根家族被 `pinned` 固定），家族内的子事件时间点没有覆盖。

建议：时间点不设 `role="button"`/`tabIndex`，按下时照常把焦点交给时间线；或者在 `onPointerDown` 中显式聚焦时间线。双击问题可以参照收起卡的做法（`PlanningWorkspace.tsx:2278-2283`，`COLLAPSE_DELAY_MS = 260`），选中后延迟一个双击间隔再变卡片，或在时间点上自行处理 `detail ≥ 2`。补充用例：点击时间点后按 Delete 弹出删除确认；家族内子事件时间点双击打开编辑器。

### 9. 拖动预览不移动时间点

拖动预览通过 `moved` 集合给元素加 `translateX`（`EventTimeline.tsx:156-162`、`:582-585`），包括被拖事件的子孙和锚定在它上面的事件（`follows`，docs/584 A3）。方案 §2.5 的 `EventPoint` 没有接收这个变换。级别 2 下拖动一张“重要”父卡，它的“一般”子事件是时间点，预览时卡片移动、时间点不动，松开后才跳过去。ZB-15 只检查拖动后时间变化。

建议：时间点同样应用 `moved` 变换；ZB-15 增加“拖动中，父卡的时间点子事件与父卡同步移动（x 差不变）”。

### 10. 状态行提示的位置偏离批准稿

设计稿把“N 个一般事件显示为时间点 · 显示为卡片”放在状态行（`index.html:355-357`，`.status .zh`）。方案 §2.3 把它移到时间线左下角浮层，理由是避免 PlanningWorkspace 重渲染。批准稿不应在实现阶段改动，而且这个理由并不成立：代码中已有 `ViewportValue`（`EventTimeline.tsx:697-700`）这种做法，状态行里放一个订阅小 store 的组件，由 `EventTimeline` 在 layout effect 中写入级别与计数，PlanningWorkspace 不会重渲染。另外，窄面板下小地图左右都贴边（`worldline.module.css:347`），左下角浮层会与它重叠。

建议：按设计稿放在状态行，用独立 store 驱动；设计稿中的级别指示条 `.lv`（“原样 / 缩小卡片 / …”）是否进入产品，需要在方案中写明（设计稿右下角的“卡片系数 · 拥挤度 d”是审核调试信息，按 AGENTS.md 不进入产品，方案没有带入，正确）。计数范围也要与设计稿一致：设计稿统计全部事件（`index.html:293`），方案写“当前视窗构建范围内”，构建范围是 7 个视窗宽（`buildRange`，`worldline-layout.ts:1495`），既不是全部也不是视窗。

### 11. 回差用的“上一级”不能在渲染中写 ref

方案 §2.3 写“`useRef` 保存上一级做回差，`useMemo` 求值”。`EventTimeline` 特意把 `timelineStep` 的状态放到 layout effect 中提交（`EventTimeline.tsx:192-198`，review R10），因为 StrictMode 或被打断的并发渲染会把渲染结果丢掉。若在 `useMemo` 中写 `prev.current = level`，被丢弃的渲染也会改动它：d 在 40–46 之间时，同一个 d 可能先后算出 2 和 1，时间点闪现。

建议：与 `state.current` 一样，在 layout effect 中提交上一级；`unfolded`、`showAll` 的清空也放在 effect 中，或者在渲染时派生（级别 < 3 时忽略 `unfolded`），不要在渲染中调用 setState。

### 12. 选中集合身份每次变化，级别 ≥ 2 时每次点击都会重排

`keep.cards` 来自选择、命中、编辑、展开。`points` 每次重新求值都是新集合，而 §2.4 规定“集合身份变化即重排”。级别 2 下点一张已经是卡片的“重要”卡，`points` 内容不变但身份变化，触发增量重排（885 事件约要重建构建范围内全部家族）。平移帧中 `hitId`、`selection` 不变，没有问题；但选择、悬停之外的每次 PlanningWorkspace 渲染都会重排。

建议：`zoomPlan` 的结果按内容比较，内容不变时沿用上一次的集合；单元测试中断言同一输入两次调用返回同一个 `points` 对象（或在 `EventTimeline` 中比较）。

### 13. 现有 `.stamp` 使用省略号，ZB-01 的断言会失败

`.stamp` 有 `text-overflow: ellipsis`（`worldline.module.css:281`，docs/585 §4 有意为之）。WU-35 只在事件表中运行，所以一直通过。ZB-01 在时间线中断言“面板内无 `text-overflow: ellipsis`”，按现有代码就会失败，与本次实现是否正确无关。

建议：ZB-01 的断言排除 `[data-stamp]`，或者在方案中决定时间戳是否也改为渐隐（这属于 docs/585 已批准的行为，若要改需说明来源）。

## P2

### 14. `settle` 在不同间距下仍正确，但前提要写进代码

现有注释（`worldline-layout.ts:1319-1321`）的论证依赖“同一列间距一致”。单趟算法按列顶排序，y 只向下移动；风险在于：y 越过某个前面已跳过的列 o1（当时 y 在它上方），之后被后面的列 o2 推下，落进 o1 的禁区。这要求同时满足：

- `g(f, o2) > g(f, o1) + (o2.y − o1.y)`，即 o2 的间距更大；
- `o1.y + o1.h + g(f, o1) > o2.y + o2.h + g(f, o2)`。

在本方案中，间距更大的一方只能是卡片（f 是卡片时：时间点 16 < 卡片 30；f 是时间点时：时间点 6 < 卡片 16），间距更小的一方只能是时间点（高 18）。卡片家族的最小高度是 34 × 0.75 = 25.5，所以第二个条件变成 `18 + 16 > 25.5 + 30` 或 `18 + 6 > 25.5 + 16`，都不成立。结论：本方案的数值下单趟算法正确。

反例说明前提的必要性：如果时间点高度为 60（或卡片最小高度小于时间点），取 f 为卡片（h = 34），o1 为时间点（y = 100，h = 60），o2 为卡片（y = 101，h = 20），二者左右并排、都与 f 横向重叠，起点 from = 50。o1：50 + 34 + 16 = 100，不碰撞；o2：50 + 34 + 30 = 114 > 101，碰撞，y = 101 + 20 + 30 = 151；此时 151 < 100 + 60 + 16 = 176，与 o1 碰撞，而单趟算法不再回头。

建议：注释写明成立条件“时间点高 + 小间距 ≤ 最小卡片高 + 大间距”，在 `packFamilies` 中加开发期断言；ZP-06 的随机盒子中加入“两个横向并排、纵向相近、类型不同的列”这一构造，不只靠随机。

### P1

#### R2-1. 手动折叠的家族在级别 ≥ 3 时点不开

§2.3 规定时间线 `folded = foldedEvents ∪ autoFolded`，没有减去 `unfolded`。第 1 轮第 2 条建议的是 `(foldedEvents ∪ autoFolded) − unfolded`。

失败情形：用户先在事件表中折叠家族 A（A ∈ `foldedEvents`），切到时间线并缩到级别 3。A 也在 `autoFolded` 中，点折叠钮走第一分支，`unfolded.add(A)`；`zoomPlan` 把 A 从 `autoFolded` 去掉，但 A 仍在 `foldedEvents` 中，并集里仍有 A，画布没有变化。按钮的 `aria-label` 仍是“展开…的子事件”（`EventCard.tsx:171`），用户再点一次，A 又从 `unfolded` 中移除，循环往复。

建议：时间线的 `folded = (foldedEvents ∪ autoFolded) − unfolded`，`foldClick` 第一分支的条件改为“级别 ≥ 3 且 A 当前在时间线上处于折叠状态”。ZB-05 增加一步：先在事件表中折叠一个家族，再到级别 3 点它的折叠钮，时间线上该家族展开，事件表中仍是折叠。

#### R2-3. 时间点“按下即双击”与卡片自己的双击会各触发一次

§2.6：lane 的 `onPointerDown` 中，若目标在 `[data-event-id=lastPointPress.id]` 内且未超过 400ms，按双击处理并调用 `ctx.onSelect(id, 2, mods)`。时间点变成卡片后，第二下通常落在这张卡片上。卡片自己的 `onClick` 在 `ev.detail ≥ 2` 时也调用 `ctx.onSelect(id, 2)`（`EventCard.tsx:161`；Chromium 的点击计数按位置和时间累计，不按元素）。两条路径都会进入 `actions.select` → `toggle(id, 2)`（`PlanningWorkspace.tsx:2296`）。

失败情形：

- 双击时间点：按下时打开编辑器（`setEventDraft`）。随后的 click 若在卡片重渲染（`p.editing = true`）之前派发，`EventCard` 的 `onClick` 不会提前返回（`:156`），`toggle(id, 2)` 再执行一次。这次 `eventDraft` 已有值，提示“请先保存或取消当前事件编辑，输入已保留。”（`:2273`），或者把草稿重置为原事件。哪种情况出现取决于渲染时机，测试会时过时不过。
- 第二下用 ⌘：`mods` 被忽略，直接进入编辑。

建议：lane 的双击分支处理后，标记本次按下已消费（例如 `consumedPress` ref），`EventCard` 的 `onClick` 遇到已消费的按下直接返回；或者只在第二下落在空白处（时间点换行后）时才由 lane 处理，落在卡片上时交给卡片的 `detail ≥ 2` 路径。ZB-10 增加断言：双击后没有出现“请先保存或取消”提示，草稿字段与事件一致；并分别测“第二下落在卡片上”和“第二下落在空白处”两种情形，用 `page.mouse` 分两次按下（中间等待一帧），不用 `dblclick()`。

#### R2-4. 估算行数决定标题高度：真实字体下的影响需要实测，夹具结果不能代表真实情形

§1.1 不测量，DOM 高度服从估算。两种误差的后果：

- 估算偏小（1 行，实际需要 2 行）：标题 `nowrap` 后被渐隐截断。按 R1 这张卡本应显示两行，所以这是不满足需求，不是样式差异。

实测（浏览器夹具，F60 的 59 个标题）：估算宽度 − DOM 宽度在 [0, 9.8]px 之间，估算从不偏小。但夹具中标题的计算字体是 `Times`（夹具不加载 `--font-ui` 用到的 Noto Sans SC，`globals.css:101`），中文字形来自系统回退字体。真实应用用 Noto Sans SC / 苹方，结果可能不同。另外，设计稿在 CSS `zoom` 下用了 6px 余量，原因是“缩放时头部按小数像素排版，刚好放下会把最后一个字挤到下一行”（`index.html:198`），方案沿用 `TITLE_SLACK = 2`。级别 ≥ 1 时 `c < 1`，刚好放下的单行标题可能出现 0.5–1px 溢出，被判定为渐隐。

建议：§8 的真实应用驱动在级别 0 和级别 2（c = 0.75）各统计一次：`data-title-lines="1"`、宽度小于上限却有 `data-fade` 的卡片数（估算偏小），以及 `data-title-lines="2"` 但自然排版只有一行的卡片数（估算偏大）。前者应为 0；若不为 0，把 `TITLE_SLACK` 调到设计稿的 6，或者让估算偏大一侧。

§2.4 让 store 持有 `EventTimeline` 注册的回调。缺少以下几点：

### 浏览器（§6.2）
