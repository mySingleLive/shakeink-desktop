# 573 世界线按小说纪年定时间 测试用例 · 独立审核

日期：2026-11-15。审核对象：`docs/573-worldline-era-calendar-cases.md`（下称“用例”）。对照：`docs/572-worldline-era-calendar-plan.md`，以末尾“评审后修订”为准（下称“方案”），以及 `docs/572-worldline-era-calendar-plan-review.md`。工作树里已有未提交的实现（`src/lib/planning/era-calendar.ts`、`desktop/core/novel-import-wizard-timeline.ts` 等）。下文的“当前实现”指这份代码，我用 `npx tsx`（Node 24.18.0）临时脚本调用它来核对期望值能否算出，脚本已删除。它不作为方案依据。本次未修改任何源文件或测试文件。

结论：**有条件通过**。用例覆盖了 R1–R14 的主干，合成纪元名、不用模型和 Key 的做法正确。但存在以下问题，改完才能实施：
- 有几处期望值不精确，或写了“±1 年”“≥”这类宽松断言，掩盖了方案自身的缺陷。EC-34 的“±1 年”会放过 `ago` 换算的年份偏差。EC-11 只检查步长，放过了刻度标签重复的问题。
- 有几处与方案或与其它用例矛盾：EC-30 的纪元列表与合成日历不符；EC-20 第二句与 R14 字面规则不符；EC-52 与线索正则的实际范围不符。
- R7“邻居跨纪元时精度为 era”、R3 第 1 步“没有 present 时取最大年份”、R3“起点必须早于后一纪元”、当前纪元之后的纪元等规则没有用例。前两条在当前实现中就是错的。
- 要重写的旧用例漏列了一大批：所有用 `date` 字段的用例都要改。
- 真实目标漏了方案验收中“重跑第 17 步提取”这一条。

## 二、必改

**必改 1：EC-30 的纪元列表与合成日历矛盾，期望值也要写成数字。**
- 第三节开头规定合成日历是“青石纪 + 赤铜纪”。按 R3，`calendar.eras` 中列出的每个纪元都会得到起点，与事件是否用到它无关。所以 `eras` 是两项：`[{name:'青石纪',start:-876582},{name:'赤铜纪',start:0}]`。青石纪长度按估算取下限 100 年，起点为 −100Y = −876582。用例写的“`eras=[{name:'赤铜纪',start:0}]`（只出现一个纪元时）”，要么改成上面的两项，要么把本用例的 `calendar.eras` 改成只有赤铜纪。方案没有“未用到的纪元不写入”这条规则，不能凭空加。
- “D(1349,6,26)、+12、+24、+48”要写成 `[11820552,11820564,11820576,11820600]`。按 R7 的较粗精度规则，两边都是 `day` 时中间也是 `day`，floor 规则与 docs/570 WT-08 相同。当前实现的结果与此一致。
- 另断言 `epoch='0001-01-01T00:00:00Z'`，名次 1、2 的 `time` 以“（按先后推定）”结尾。

**必改 2：EC-34 的“±1 年”要去掉，并补一条“ago=1”的用例。方案的 `ago` 公式会少算一年。**
- 按 R3 第 2 步，`ago` 的值是 `civilDays(present.year,1,1)×24 − ago×Y`。`present.year=1349`、`ago=20` 时，值为 11816328 − 175316.4 = 11641011.6，也就是第 1329 年 1 月 1 日 0 点之后约 11.6 小时，显示 `赤铜纪1329年`。这条可以写死，不需要“±1 年”。
- 问题出在公式从 `present.year` 的 1 月 1 日 0 点往回减平均年，再取所在的历年。中间若平年居多，减出来的值会比目标年的 1 月 1 日早几个小时，落到再前一年。`present=1349` 时 `ago=20`、`ago=1` 恰好正确（中间含闰年 1348）。换成其它年份就会差一年，我实测：
  - `present=1302, ago=1`：1302-01-01 0 点 − 8765.82 小时 = 1301-01-01 之前 5.82 小时，显示 `赤铜纪1300年`，应为 1301 年；
  - `present=1301, ago=3`：显示 `赤铜纪1297年`，应为 1298 年。
  读者看到“一年前”显示成两年前，这是错误结果，“±1 年”的断言会放过它。
- 要求：先由方案定下规则，例如“`ago` 落在当前纪元内时，显示年份 = `present.year − ago`，值取该年 1 月 1 日”（即值 = `civilDays(present.year−ago,1,1)×24`，非整数 `ago` 向下取整）。然后 EC-34 改为两组精确值：`ago:20` → 值 `D(1329,1,1)=11640960`（按新规则）、显示 `赤铜纪1329年`；`ago:1`，`present.year=1302` → 显示 `赤铜纪1301年`。如果方案坚持原公式，用例也必须写出 `ago:1` 的实际显示，并在方案中把这一年的偏差写成已知限制。
- `ago:0` 当前实现接受（值为 `D(1349,1,1)`），而校验写的是 `ago` 取 0..1e6、当前实现的 `validAgo` 却要求 `>0`。EC-46 要写明 `ago:0` 是保留还是丢弃。

**必改 3：EC-35、EC-36 的数据测不到要测的规则。**
- EC-35：`ago:1400` 的值是 `D(1349,1,1) − 1400Y` = −455820，超出赤铜纪起点 52.0 年（A=51.9997）。估算长度 = 51.9997×1.1+10 = 67.2，取下限 100 年。所以“≥ (1400−1349)×1.1+10 且 ≥ 100 年”实际只测到了下限，A 是否参与估算完全看不出来。改为 `ago:1500`：A=151.9997，长度 = ⌈151.9997×1.1+10⌉ = 178 年（`round` 得 177，方案写“取整到年”，要明确是向上取整），青石纪起点 = −178Y = −1560315.96，名次 0 的值 11816328 − 1500Y = −1332402 落在其中，精度 `era`。期望写成这些精确值。
- 再补一个负例：青石纪之前还有“玄土纪”。`ago:1500` 只算进紧邻的青石纪，玄土纪的长度只按自己的显式年份估算（无年份时为 100 年），起点 = −278Y。这是 R3“其它纪元的 A 为 0”的唯一保护。
- EC-36：数据中赤铜纪是当前纪元，起点固定为 0，它的 `startAgo:1349` 不参与计算。按公式它对应的值是 −8763.18，与 0 不一致，用例要写明“当前纪元的 `startAgo` 被忽略”。青石纪起点 = 11816328 − 2349×8765.82 = −8774583.18。用例写“取整到小时”，方案 R3 没有取整这一步，当前实现用了 `Math.round` 得到 −8774583。要先在方案里写明是否取整，再写死其中一个值。
- 补 R3“起点必须严格早于后一纪元，否则改用估算”：青石纪 `startAgo:1000` 时，`D(1349,1,1) − 1000Y` = 3050508 > 0，不早于赤铜纪，改用估算，起点为 −876582。当前实现结果一致。

**必改 5：R7“两个邻居属于不同纪元时，精度为 `era`”没有用例，当前实现也没做。**
数据：名次 0 青石纪12年（`year`），名次 1 无日期，名次 2 赤铜纪1349-06-28（`day`）。按 R7，名次 1 精度为 `era`，值为 (−780174+11820600)/2 = 5520213，显示 `赤铜纪`。我实测当前实现给出 `year`，卡片会显示“赤铜纪629年”这种捏造的年份。这正是用户要避免的结果，要单列 EC-41b。

**必改 6：EC-20 的第二句与 R14 矛盾，第一句依赖未写明的边距。**
- R14 的规则是“覆盖至少 80% 事件的最短连续区间”。事件均匀分布时，这个区间只有全长的 80%，不等于 `fitTimelineWindow` 的结果。用例写的“均匀分布时与 `fitTimelineWindow` 相同”，靠的是当前实现额外加的条件（`dense.span×20 < full.span` 时才收窄），方案里没有这一条。要求方案补上这个阈值（或别的判定），用例按它写，并补一条刚好越过阈值的数据。
- 第一句的数据：100 个事件中 95 个均匀分在 0..1000、5 个在 −1e7 附近。80 个最密事件只覆盖约 0..840（79×1000/94）。在宽 1412 时窗口为 `{start:−47.45, span:1161.82}`，能盖住 0..1000 只是因为两侧留了边距。这里还有等宽区间的平局（多个起点的宽度在浮点误差内相等），起点取哪个也没写。要求：断言改为“窗口包含 80 个最密事件、不含 −1e7”，并写明平局取最早的区间。
- R14 规定只对带纪元的日历生效，EC-20 是纯函数用例。要在面板一侧补一句断言：无纪元的世界线打开后窗口等于 `fitTimelineWindow`。可并入 EC-74。

**必改 7：EC-51、EC-52 要按方案写清边界，并补负例。**
- EC-52 期望摘出“青石纪末年”。方案写的是“含‘纪/纪元’的句子”，用例按方案写是对的。但当前实现的正则只认“第X纪”和“XX纪元”，实测只摘出 2 句，漏了“青石纪末年”。实现要改，用例保留。
- 反过来，方案“含‘纪’”的写法太宽，“年纪”“纪律”“世纪”“纪念”都会被摘进来，占掉 120 句的名额。用例要加这几个负例，方案要把规则收紧（例如“汉字 + 纪 / 纪元”且不是上述常用词）。
- EC-52 还要补：线索超过 120 句时只保留前 120 句（构造 130 个不同句子）；同一句含多处匹配只摘一次。
- EC-51 写“`三年前` → 无”。当前实现从原文时间词里解析出 `ago`：`三年前` → `{ago:3}`，`二十多年前` → `{ago:20}`，`一千三四百年前` → `{ago:1350}`。方案只让原文时间词补纪元和年月日，`ago` 只由模型给出。用例与方案一致，要保留，并补上 `二十多年前`、`一千三四百年前` → 无 `ago`。如果方案改为允许从原文取 `ago`，要先改方案，并写明“一千三四百”取多少。

**必改 8：EC-11 只查步长，放过了刻度标签错位。**
刻度位于 Y 的整数倍，但纪元内的年份从 `civilDays(y,1,1)` 开始。两者相差不到一天，就会让标签重复或跳号。实测纪元起点 0，刻度 k×Y 按 `year` 显示：3Y、4Y 都显示 `赤铜纪4年`（4Y = 1460.97 天，第 5 年 1 月 1 日是第 1461 天），7Y 与 8Y 都是 `赤铜纪8年`，第 5、9 年不出现。跨 15 年、宽 1412 时，刻度标签为“赤铜纪1340年12月、1343年1月、1344年12月……”。要求：
- EC-11 断言相邻刻度标签互不相同，且按年刻度时每个标签都是整年（不含“月”）；
- 方案把“刻度年长取 Y”改为刻度落在 `civilDays(纪元年,1,1)` 上（或按年刻度时显示规则取四舍五入后的年份）。

## 三、浏览器用例（EC-73、EC-74）的可行性
