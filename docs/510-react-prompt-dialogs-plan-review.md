# 510 方案 · 独立审核

日期：2026-11-05。对象：`docs/510-react-prompt-dialogs-plan.md`。依据当前工作树（`feat/novel-import-roster-speed`，干净）的源码和测试，未修改任何源文件。

## 结论：需修订

替换范围基本准确。`grep showMessageBox|showErrorBox desktop/ src/` 的结果与第1节表格逐行一致（`index.ts:241/433/461/462/530/534/558/836/884/981`，`root-relocation-window.ts:69/118`），`src/` 下没有调用。关闭协调器的 `current()` 检查和 `releaseOwner` 时序能避免“窗口已销毁后才回答”的死锁。但方案有四处需要修订后才能实现：一是渲染器卡死时无法应答，这正是截图那个框最常出现的场景；二是 Esc 会同时关闭下层对话框；三是按钮按下标映射，容易错位；四是 smoke/E2E 脚本没有列入改动范围。

## 发现

1. **（高）“尚不能关闭”框最常见的触发原因就是渲染器无响应，HTML 框在这种情况下画不出来。** `failed()` 在 `flush` 抛错后调用（`close-coordinator.ts:60-64`）。`flushDraftForClose` 等待 `closeChannel.request`（`index.ts:289`），渲染器 20 s 内不回复就超时抛错（`renderer-close-channel.ts:6,10`）。也就是说，渲染器主线程卡住（长任务、死循环、GPU 挂起但进程未退出）时必然走到 `failed()`，这时 HTML 提示无法渲染，也无法应答。这种情况不会触发 `render-process-gone`，所以 `cancelAll` 也不会执行。之后再次关闭或退出都会复用同一个 flight（`close-coordinator.ts:24`，`index.ts:483-486` 的 `before-quit` 也走 `beginClose`），应用只能被强制结束。原生框不依赖渲染器，所以现在能救场。第3节把这写成“可接受的差异”，但这是该框的核心场景，不是边缘情况。要求：`ask` 增加“渲染器已显示”回执（PromptHost 打开后调用 `ackPrompt(id)`），N 秒内没有回执，或者 `webContents` 发出 `unresponsive`、不存在可用窗口时，回退到原生 `showMessageBox`，按钮映射不变。这偏离了“全部改为 HTML”的字面要求，需要在结论里告诉用户并取得确认。配置重置的降级工作台（第4条）同样需要这个回退。
2. **（高）Esc 会被多个对话框同时处理。** base-ui 的 `useDismiss` 在 `document` 上注册 keydown（`node_modules/@base-ui/react/floating-ui-react/hooks/useDismiss.mjs:458`）。不同 `Dialog.Root` 不在同一 FloatingTree 中，`hasBlockingChild` 判断不出层级（`:99`）。`stopPropagation`（`:108-110`）也挡不住同一节点上的其他监听器。因此按 Esc 回复 `cancelId` 的同时：
   - 迁移确认（`index.ts:558`）由设置页的 `DataRootMigrationButton` 发起（`SettingsDialog.tsx:66`，`DataRootMigrationButton.tsx:12`），Esc 会顺带关闭设置窗口（`SettingsDialog.tsx:62` 中 `onOpenChange={onOpenChange}`）。
   - 导入目录锁修复确认（`index.ts:241`）从 `NovelImportDialog` 发起，Esc 会触发 `close()`（`NovelImportDialog.tsx:175-180,217`），导入窗口被收起或弹出关闭确认。
   - `confirmStop` 由用户关闭窗口触发，下层可能是任何普通对话框。
   要求：PromptHost 在 `window` 捕获阶段处理 Esc，并 `stopImmediatePropagation`，或者用 `onOpenChange` 拦截后统一由宿主处理。浏览器用例需覆盖“设置/导入窗口打开时出现提示，按 Esc，下层窗口保持不变”。方案里“点击遮罩→cancelId”也会和下层窗口的外部点击逻辑交叉（`SettingsDialog.tsx:36-55` 在捕获阶段拦截 pointerdown，判断依据是矩形区域）。建议对齐 `ni-close-confirm` 与引导的做法，使用 `disablePointerDismissal`（`OnboardingController.tsx:70`），遮罩点击不作回复。
3. **（中）提示打开后若有别的模态框后打开，提示会被标记 `aria-hidden` 并失去焦点。** base-ui 打开模态框时，只对当时已存在的 body 子节点执行 `markOthers`，设置 `aria-hidden`（`FloatingFocusManager.mjs:328-347`），并且把 `initialFocus` 移到自己身上。z-index 只决定视觉上谁在上层。降级工作台的情况最典型：临时根目录的引导未完成（`onboarding-flow.ts:4-6`），`OnboardingController` 在 bootstrap 完成后立即打开（`DesktopApp.tsx:52,190`）。配置重置提示在加载分支（`:181`）就已经通过拉取显示出来，分支切换后 PromptHost 会重新挂载，先后顺序不确定。结果可能是：屏幕上看到提示，读屏器看不到它，焦点和 Enter 落在引导上。`model-required`、恢复窗口等也可能在提示期间打开。要求：有待答提示时压住其他对话框（把 `normalDialogs`、引导 `suspended` 与之联动，参照 `DesktopApp.tsx:184-189` 的现有模式）；PromptHost 放在三个分支外的同一位置，避免重新挂载；补充“提示先于引导或设置打开”的浏览器用例。
4. **（中）配置重置的降级工作台：拉取设计能显示提示，但取消即退出的行为和回退都有问题。** `launch()` 在 `createWindow` 里等到 `loadURL` 完成（`index.ts:949`），然后 `confirm` 才提问（`:980-983`）。这时 React 还没挂载，事件会丢失，靠挂载时拉取可以补上，这一点成立。错误分支也挂载了 PromptHost，所以 bootstrap 失败时提示仍然可见。问题有三：(a) 错误分支的“重新打开工作台”按钮会执行 `location.reload()`（`DesktopApp.tsx:180`），这属于新文档导航，会调用 `releaseOwner`（`index.ts:944`），于是 `cancelAll` 返回 `cancelId=0`，即“退出”，应用随即静默 `app.exit(0)`（`config-reset-offer.ts:21`）。建议这一类提示在 `releaseOwner` 时保留在待答表，交给新文档重新拉取，不直接取消；或者在方案中明确“重载即退出”。(b) 前端包无法加载时没有任何提示，见第1条的回退。(c) 第1节说 `index.ts:987` 的 `fatal` 发生在“窗口尚未创建”时，这不准确：`wipe()` 失败会在降级窗口已经打开时调用 `fatal`（`config-reset-offer.ts:22`）。`:1044` 的 catch 同理。可以保留原生框，但理由要改成“退出前的最终错误”。
5. **（中）回复按下标映射，调换按钮顺序容易造成语义错位。** 第2节同时要求“按钮按数组顺序”和“视觉顺序为 [取消类…, 主操作]”。现有数组的顺序并不统一：`failed()` 是 `["重试","导出草稿","取消关闭"]`，`cancelId` 为 2（`index.ts:462`）；定位确认是 `['使用原目录并重新打开','取消']`，`cancelId` 为 1（`root-relocation-window.ts:69`）；配置清空的下标 1 对应“删除全部文件”（`index.ts:981`）。重排数组后，每个调用处的 `response===N` 都要同步修改，smoke 脚本里写死的 `response` 也要改（第7条）。建议 `buttons` 带稳定的 `value`（例如 `'retry'|'export'|'cancel'`），`reply(id,value)` 只接受该提示声明过的值，渲染顺序与语义分开。至少应要求：破坏性操作（清空配置、修复锁）的默认值和 `cancelId` 都指向非破坏项，并为每个调用处写单测断言映射。
6. **（中）安全：确认从原生 UI 移到渲染器后，渲染器代码可以伪造“用户已确认”。** 新的两个 handle 只做 `trusted(event)` 检查（`index.ts:142-144`）。只要能在主框架执行脚本，就能对待答提示直接调用 `replyPrompt(id,1)`，从而触发清空全部配置并重启（`index.ts:981`，会删除包括作品在内的整个目录）、移除作品锁（`:530`）或迁移（`:558`）。原生框是渲染器无法伪造的用户在场证明，`assertConfirmed`（`index.ts:236`）的设计也依赖这一点。主框架本来就是受信源，这不算新的越权，但确认强度确实降低了。方案应写明这项取舍，确认主框架不渲染未经净化的导入正文或 Markdown HTML。reply 校验还需补充：id 必须是当前显示的提示，同一 id 只接受一次（第2节已提到），以及 `index` 或 `value` 的 zod 严格校验。新增 handler 不经 `businessGate` 是正确的，因为关闭期间 gate 已关闭（`index.ts:451`）。
7. **（中）验证范围漏掉了直接替换 `dialog.showMessageBox` 的真实 Electron 脚本。** 改造后这些替换不再生效，脚本会卡在 HTML 框上，或者断言失效：
   - `scripts/run-lotm-wizard-import.mjs:56`：自动回答“停止任务并继续”，LOTM 导入 E2E 驱动依赖它。
   - `scripts/smoke-work-lease.mjs:26`，`scripts/verify-works-loading.mjs:70-74`：作品锁确认与结果通知。
   - `scripts/smoke-runtime-migration.mjs:29,32`：迁移确认。
   - `scripts/smoke-root-relocation.mjs:67`：定位确认。
   - `scripts/verify-novel-import-close-states.mjs:66,129`：断言原生框计数为 0，改造后恒成立，需改为断言没有出现 HTML 提示。
   - `scripts/smoke-work-restore.mjs:31,34`，`scripts/smoke-application-restore.mjs:89`：如果仍在台账中，需要处理；已退役的应在方案中说明。
   单元测试除方案已列的之外，还需更新：`root-relocation-window.test.ts:61`（handler 列表精确等于 `[state,command]`）、`:83`（preload 键精确等于 `['command','state','subscribe']`）、`root-relocation-100-review.test.ts:146`、`root-relocation-navigation-100-review.test.ts:40`、`work-lease-main.test.ts:42`（按 `dialog:修复异常退出锁` 断言事件顺序）、`work-lease-main-review.test.ts:48`（`signal` 透传）、`root-maintenance-main-review.test.ts:28,104,113`（closeRig 的 `response` 桩）、`novel-import-integration.test.ts:153`、`repository-license-commands.test.ts:28`（about 的 `onError`）。`close-ipc-review`、`profile-ipc`、`configuration-files-review` 用固定的标识符列表执行 `registerIpc()`（如 `profile-ipc.test.ts:35`），新 handler 只能在函数体内引用 `appPrompts`，不能在注册时求值，否则这些测试会报 ReferenceError。`config-reset-offer.test.ts`、`startup-recovery-main.test.ts`、`inbox-lease-*` 不受影响。
8. **（低）work lease 交接可以使用 HTML 提示，但需要补用例。** `confirm` 在 `afterClose → finishClosed` 中执行（`index.ts:459`、`work-lease-handoff.ts:122,134`）。这时 gate 已关闭，渲染器的 `closing=true`，显示“正在保存并关闭”（`DesktopApp.tsx:192`，`onOpenChange` 为空操作，所以 Esc 不会影响它），提示叠在 z-index 70 上可以应答。`AbortSignal` 来自 `controller.abort()`（`work-lease-handoff.ts:72`），`ask(…,signal)` 撤下提示时返回 `cancelId`，结合 `:531` 的 `!signal.aborted` 语义不变。`notice()` 只有一个按钮，被 `cancelAll` 取消后 `assertOwner` 会抛错，行为与原先一致。重试交接失败时，“重试交接/稍后重试”会叠在 `WorkLeasePendingDialog` 之上（两者同时打开），需要用例覆盖。PromptHost 必须放在 `inert={leasePending}` 的 div 之外（`DesktopApp.tsx:186`），方案应写明。
9. **（低）无窗口时的行为变了。** 原先 `confirmStop` 和 `failed` 在没有窗口时会弹出 app-modal 原生框（`index.ts:433,461,462` 的 `window?…:showMessageBox(options)`）。方案改为 `publish` 返回 false 后直接取消。macOS 只关闭窗口后从 Dock 退出时，这会静默阻止退出。这种情况“不在已有窗口之上”，按第1节自己的范围定义，应该保留原生分支，可与第1条的回退合并。
10. **（低）定位窗口加通道可以接受，但通道名需要区分。** `trusted` 精确比较 `shakeink://app/` 并检查 `ownerAlive`（`root-relocation-window.ts:79-81`），新 handle 沿用即可。`render-process-gone` 和新文档导航已把 `ownerAlive` 置为 false（`:101-104`），这里应同时调用 `cancelAll`。确认期间，窗口的 `close` 会等待 `workFlight`（`:94-98`），与原生框一样要等用户应答，不构成新的死锁。方案里事件和 handle 都叫 `desktop:relocation-prompts`，建议事件改为 `desktop:relocation-prompt-event`，避免混淆。
11. **（低）关于窗口和菜单错误可以简化。** `executeJavaScript` 不受页面 CSP 限制，可行；更简单的做法是把错误段落直接写在 HTML 里，在 `onError` 中切换。菜单命令失败（`index.ts:836`）改用已有的 sonner `toast.error`（`DesktopCommandController.tsx:43` 已这样做）更轻，不必占用一个模态。
12. **（低）台账。** AGENTS.md 要求更新 `docs/requirements-traceability.json`，方案第4节没有提到；需要补测试用例文档，并交独立审核。
