## 根因事实（已在真实数据上验证）

### 现象链

1. 模型把 `operations` 数组序列化成字符串：`{"operations": "[{\"kind\": \"put\", ...}]"}`。
2. 该字符串**内层 JSON 自身非法** —— 不是截断，而是**闭合符错位**：模型多写或少写 `}` 与 `]`，括号深度失衡。
3. `src/lib/ai/tool-input-repair.ts` 的 `parseEncodedContainer` 只在「字符串是合法 JSON 且与 schema 类型同构」时还原容器。内层 JSON 非法 → `JSON.parse` 抛错 → `catch` 返回 `undefined` → `repairToolInput` 返回 `null` → 放弃修复 → 工具入参校验失败。
4. 模型改用紧凑格式重试，每次仍产生新的错位形态；`hasRepeatedToolFailure` 按「工具名 + 完整入参」去重，模型微调文案即绕过 3 次上限，空转持续。
5. 最终模型流末尾抛出 `AI_InvalidResponseDataError: Expected 'function.name' to be a string.`，整轮终态 `STREAM_INTERRUPTED`，界面显示「生成中断，工具结果待确认，请先核对已保存的改动」。

## 实施范围

### 唯一代码改动点：`src/lib/ai/tool-input-repair.ts`

在 `parseEncodedContainer` 内部，当「字符串以 `{`/`[` 开头」但 `JSON.parse` 失败时，追加一层**保守的闭合符修正**，成功后按既有 `matchingContainerSchema` 路径继续规整内部字段。

新增一个纯函数（建议命名 `repairContainerClosers`），职责严格限定：

**输入**：一个以 `{`/`[` 开头、以 `}`/`]` 或其他字符结尾的字符串。

**处理**：单次线性扫描，维护一个容器类型栈（`{` 或 `[`），并跟踪字符串字面量状态与转义状态：

- **转义口径**：沿用既有 `repairPlanningClosingBoundary`（`tool-input-repair.ts:14-23`）的**通用 `escaped` 标志** —— 任何 `\` 后的字符均被消费（不限于 `\"`）。不得只识别 `\"`，否则合法 JSON `"C:\\"` 会被误判为字面量未闭合而放弃修复。`\uXXXX` 按「消费 `\` 与 `u` 两字符、其余 4 位十六进制按普通字符处理」实现。
- 处于字符串字面量内时，只识别转义与闭合 `"`，其余字符（含 `}`/`]`/`{`/`[`）一律视为字面量内容，**不做任何改写**。
- 遇到开括号：入栈，原样保留。
- 遇到闭合符：
  - 栈为空：多余闭合符，**丢弃**（计入 `dropped`）。
  - 栈顶类型与该闭合符不匹配（如栈顶是 `{` 却遇到 `]`）：**改写**为栈顶类型对应的闭合符（计入 `rewritten`）。
  - 类型匹配：原样保留，出栈。
- 扫描结束仍有容器未闭合：按**栈顶→栈底（LIFO，后进先出）**顺序**补齐**对应闭合符（计入 `padded`）。
  - 注意：必须 LIFO。若按「栈底→栈顶」字面实现（先补栈底），会产出 `..."title":"标题"}]}` 这类非法 JSON，parse 失败。
- **字面量未闭合判定**：扫描结束时若 `inString === true`，说明尾部内容被切断在字符串字面量内部，**立即放弃修复**（不补齐、不放行）。

**输出**：修正后的字符串 + 统计（`rewritten` / `dropped` / `padded`）。

### 放行条件（求值顺序固定，全部通过才放行）

按以下顺序求值，任一不满足即**放弃修复、保持原值**：

1. **字面量完整性**：扫描结束时 `inString === false`（字面量已闭合）。否则放弃。
2. **闭合符错乱信号（单一表述）**：`rewritten ≥ 1`。
   - `rewritten` 是「闭合符类型与栈顶不匹配而被改写」的次数。它为 0 说明输入**从未出现类型错位**，只可能是尾部缺闭合符或纯多余闭合符 —— 这类形态可能来自真截断，也可能是模型的轻错，两者无法区分，故一律放弃。
   - `rewritten ≥ 1` 说明模型确实写错了闭合符类型。这是本次修复的唯一放行信号。
   - 附加约束：`padded ≤ 1`。多层补齐无法区分「尾部缺多层」与「中间缺闭合符」，属结构级歧义，放弃。
   - 已用真实 5 份样本复核：`rewritten = 2/1/1/2/2`、`padded = 0/1/1/0/0`，全部满足 `rewritten ≥ 1` 且 `padded ≤ 1`，全部放行且解析出 1 个合法 operation。
   - `dropped` 不参与放行判定，不设上限（真实样本含 `dropped=1` 仍放行）；它仅作为统计量返回。
3. **解析成功**：修正后 `JSON.parse` 成功。
4. **类型一致**：解析结果的容器类型与 schema 声明类型一致。判定口径**沿用既有 `matchingContainerSchema`**（`tool-input-repair.ts:134-148`）：schema 同时允许 `object` 与 `array`（`anyOf`/`oneOf`）时，按解析结果的实际类型命中分支，不另立标准。

> 说明：条件 2 **不再**声称「真截断一定 `rewritten === 0`」——复审已证伪该命题（见「范围收窄声明」）。本条件只作「模型确实写错了闭合符类型」的必要条件，不作充分条件。

### 范围收窄声明（复审第四节第 1(a) 项）

**本次修复明确不覆盖**：「模型已写错闭合符类型」**且**「输出随后被截断」的复合形态。

该形态的最小反例（复审给出，已独立复现确认）：

```
输入： [{"kind":"put","collection":"cards","value":{"id":"c1","title":"标题一","content":"正文一"]}
统计： rewritten=1, dropped=0, padded=1, inString=false
判定： 条件 2 放行
结果： 解析出 1 个 operation，而模型本意 2 个
```

原因：「类型错位」与「截断」在同一字符串上**原理上不可区分** —— 截断发生在内容中间时，剩余内容里的闭合符仍可能是错位的。复审已试过两种第二判别信号（「改写只落在尾部闭合符区」「内容区单独补齐后自洽」），**均未能拦住该反例**，故不引入未经充分验证的规则。

**取舍**：该形态下修复会产出「operation 数量少于模型本意」的提案。选择接受这一残留风险，理由见下方「残余风险与安全网」。

### 残余风险与安全网

该残留形态的后果与既有安全网：

1. **产出的是候选提案，不是作品内容**。`proposePlanning`（`src/lib/services/planning.ts:545-597`）只把提案写入 `contentVersion`（`targetType: "PlanningProposal"`，`planning.ts:578-587`），**不写 `planningDocument`**，当前规划不改变（已终审逐行核实属实）。
2. **落库路径存在提示词级确认约束，但代码层不强制**。提案保存后返回的 message（`planning.ts:595`）与 `applyNovelPlanningProposal` 的工具描述（`planning-tools.ts:81`）都要求模型先经 `askUserQuestion` 取得作者明确同意才调用 apply；`applyPlanningProposal`（`planning.ts:619-627`）本身**不校验确认状态**，纯信任模型自律。因此残缺提案会被 `pendingPlanningProposals`（`planning.ts:641-659`）列进 `pendingProposals` 暴露给模型；若模型不守约，可能在无作者确认时自动采用。安全网强度为「**弱（提示词约束为主）**」，非代码级强制。
3. **作者可见性依赖模型走确认流程，非强制环节**。确认面板由 `nextPlanningProposalApproval`（`planning.ts:665-679`）与模型的 `askUserQuestion` 承载；若模型不走确认流程直接 apply，作者只能事后从规划历史察觉。
4. **operation 内部截断通常本就不可修复**。终审实测：截断落在 operation 内部且伴随类型错位（如尾部悬挂 `,`）时修正后 `JSON.parse` 仍失败，被条件 3 拦下；截断在字面量内被条件 1 拦下；纯内部截断（`rewritten === 0`）被条件 2 拦下。2000 例随机变异中放行 190 例、其中 op 数缺失 13 例（均为整块 operation 缺失形态）——穿透的只丢整块，不改内容（骨架比对 0 例不一致）。

即：最坏后果是「一个内容偏少的候选提案进入 `pendingProposals`，模型自律失守时可能被自动采用」，而非「作品内容被静默伪造」—— 修复本身只改闭合符，不增删任何 ID、版本、文案；被截断的内容是模型输出本就缺失的部分。这与仓库「不臆造内容」的纪律不冲突，但提示词级安全网强度有限，验证阶段不得把它当代码级保障引用。

### 内容字符未变：从运行时门禁降级为测试期断言

原「放行条件 5（内容字符未变）」在运行时**无法独立验证**：若比对与修复共用同一扫描器，扫描器自身的缺陷会让两侧同时错、比对仍判「未变」（复审 N5 实测：共用缺陷逻辑漏检，独立扫描器才检出）。

因此本次**取消运行时门禁 5**，改为**测试期断言**：

- 断言形式：按字面量边界分段比对，**参照物必须是独立于被测实现的正确实现**（不得复用被测扫描器）。
- 断言目标：所有字面量内片段字节完全未变；字面量外片段仅在闭合符位置有差异。
- 该断言只用于验证实现正确性，不参与运行时放行决策。

### 已知不可消歧的边界（显式声明，本次不覆盖）

- **中间缺闭合符 vs 尾部缺闭合符**：同一字节串 `{"a":{"b":1,"c":2` 可对应两种意图（`{"a":{"b":1,"c":2}}` 或 `{"a":{"b":1},"c":2}`）。补齐只发生在尾部，无法识别中间缺失。本次修复**只覆盖「至少有一处类型错位」且 `padded ≤ 1` 的形态**；`rewritten === 0` 的中间缺失一律放弃（条件 2）。
- **「类型写反」与「漏写开括号」不可区分**：`{"a":1]`（模型本意 `{"a":[1]}`）会被改写为 `{"a":1}`，数组结构静默丢失。本次不覆盖该形态 —— 它要求模型漏写开括号，与实测形态（闭合符类型/数量错乱、内容完整）不同。
- 上述两类均属供应商输出的更罕见形态，本次以「宁可放弃修复、保留入参非法提示、由模型重试」为既定取舍。


### 为什么不放在 `parsePlanningToolJson`

`parsePlanningToolJson` / `repairPlanningClosingBoundary` 处理的是**顶层 tool call JSON**（`proposeNovelPlanning` 专用入口），其边界纪律要求已核验 `completePut` 等结构证据。本次的缺陷在**被序列化进字符串之后的内层内容**，顶层 JSON 本身合法（`{"operations": "..."}` 能正常 parse），走的是 `normalizeToolInput` → `parseEncodedContainer` 这条通用容器还原路径。

放在 `parseEncodedContainer` 的理由：这不是 `proposeNovelPlanning` 独有的问题，任何「数组/对象参数被字符串化」的供应商行为都会命中同一条路径。

**本次是通用容器路径修复**（改动点只有一个函数，所有工具自然覆盖），不是仅针对 `proposeNovelPlanning` 的特例。随之而来的影响面必须在用例中显式覆盖，至少包含：

- `proposeNovelPlanning.operations`（数组，本次故障主体）
- `updateCharacter.bigFive`（可空对象，`src/lib/ai/tools.ts` 中 schema 类型为 `{object, null}`）
- `upsertAttribute.options` / `targets`（`src/lib/ai/tools.ts:1297-1299`）

这些工具与 issue #15 的直接故障无关，但共享同一函数；若不覆盖，属于未声明的影响面扩大。

### 与既有纪律的一致性

- 既有 `parseEncodedContainer` 的三条前置判据全部保留：schema 必须明确期望 `object`/`array`（含 `anyOf`/`oneOf` 展开）、联合同时允许字符串时不处理、普通字符串字段不处理。
- 「不臆造内容」纪律：本次只动闭合符，不新增/删除任何 ID、版本、文案、数组元素。
  - **内容缺失（真截断）必须被拦截**：靠放行条件 2（`rewritten ≥ 1`）实现，而非仅靠「字面量未闭合」。否则会出现「补出结构完整但内容残缺的提案」且业务 schema 拦不住（`value` 是 `z.record(z.string(), z.unknown())`，任意内容都合法）——审核 D1 已实证该风险。
  - 「中间缺闭合符」的结构级歧义以条件 2 兜住，本次不覆盖（见「已知不可消歧的边界」）。
- `toolInputIssueHint` 不改：入参非法时的提示仍按既有逻辑区分「缺少字段」与「类型不符」。

### 已知会放行的形态（非「必须不修复」，不拦截）

| 输入形态 | 实际行为 | 说明 |
| --- | --- | --- |
| **已写错类型 + 后续截断**（复合形态，如 `[{"kind":"put",…,"content":"正文一"]}`） | **放行**，产出 operation 数量少于模型本意的候选提案 | 原理上不可区分（截断剩余内容里的闭合符仍可能是错位的），本次**不拦截**；用例应如实断言其放行为「已知残余」，不得断言为「不修复」。风险接受依据见「范围收窄声明」与「残余风险与安全网」 |
| 普通字符串字段内容像 JSON | **不修改** | 既有 `parseEncodedContainer` 前置判据 |
| `string \| object` 联合 | **不修改** | 既有 `parseEncodedContainer` 前置判据 |
| 字符串不以 `{`/`[` 开头 | **不修复** | 既有 `parseEncodedContainer` 前置判据 |

### 必须能修复（正例）

| 输入形态 | 期望行为 |
| --- | --- |
| 含类型错位的真实故障形态（真实 5 样本） | 还原为合法数组，通过 `operationSchema` |
| 合法 JSON 结尾是 `\\`（转义反斜杠） | 正常修复（不得误判未闭合） |
| 合法 JSON 含 `\uXXXX` | 正常修复 |

### 判据说明

「字面量未闭合」**不是**「真截断」的通用判据（审核 D1）。截断点落在字面量之外时该判据失效。本次放行的唯一内容信号是 `rewritten ≥ 1`（模型确实写错了闭合符类型）；真截断若不伴随类型错位（`rewritten === 0`）必被拦截。



## 测量与验收

- 单元用例（`tests/unit/tool-input-repair.test.ts` 扩充）：
  - **正例**：真实 5 样本形态（均含类型错位）各有用例，还原后通过 `operationSchema` 校验。
  - **正例补充**：含类型错位的 3 类缺陷组合 —— ①类型错位 ②类型错位+多余闭合符 ③类型错位+缺失闭合符，各有用例。
    - 注意：**单独**的多余闭合符 / 缺失闭合符（`rewritten === 0`）**不在修复范围**，对应反例用例期望「不修复」。
  - **测试期断言**：按字面量边界分段比对，参照物为**独立于被测实现的正确实现**（不复用被测扫描器）；断言字面量内片段字节完全未变、字面量外片段仅闭合符位置有差异。该断言不参与运行时放行决策。
  - **差分测试（终审建议）**：以合法 JSON 文档为种子，随机注入「闭合符替换/删除/插入/截断」（固定种子保证可复现，建议 ≥2000 例）；对放行例断言「骨架与原串逐字符一致」+「parse 结果 op 数 ≤ 原 op 数」；对拒绝例断言返回放弃。终审实测该方法秒级完成。
  - **元缺陷注入（终审建议）**：对 3 类典型错误实现（忘记字面量状态、FIFO 补齐、把字面量内闭合符计入 `rewritten`）逐一跑测试集，断言测试集**能抓住**每一种错误实现——直接验证用例集的判别力。
  - **反例**：字面量内截断、数字字面量中间截断、关键字中间截断、`,`/`:` 后截断、`\uXXXX` 中间截断、仅多余闭合符、仅缺失闭合符、中间缺闭合符、多层补齐 → 均**不修复**；类型不符 → 不修复；普通字符串 / 联合 → 不修改。
  - **正例（转义）**：`\\` 结尾与 `\uXXXX` → 正常修复。
  - **通用路径覆盖**：`proposeNovelPlanning.operations`（数组）、`updateCharacter.bigFive`（可空对象）、`upsertAttribute.options`/`targets`（数组）。
    - 注意：复审指出 zod v4 `z.toJSONSchema` 产物偶发缺 key，会使「5 个维度全部规整为数字」的断言存在偶发失败风险；用例应改用**生产同源**的 schema 构造方式（`asSchema(...).jsonSchema`），避免该不稳定因素。
  - 既有 9 个用例全部保持通过（#8 的对象/数组还原、联合不改动、错误提示区分缺失与类型不符等）。
- 集成验证：`npm run test`（tests/unit + tests/integration）全量通过。
- 类型检查：`npm run typecheck` 通过。
- 真实目标系统验证：本机以**本地真实数据根**启动桌面版，复现同一场景（让模型修改已接入规划的作品叙事卡），确认 `proposeNovelPlanning` 不再因入参非法失败、提案正常落库。执行步骤与证据留存见后续用例文档与验证文档。

## 回滚与风险

变更仅在 `src/lib/ai/tool-input-repair.ts` 的容器还原分支，回滚该提交即恢复既有行为，无数据迁移、无 schema 变更、无 IPC/协议变更。

主要风险与对应缓解：

| 风险 | 缓解 |
| --- | --- |
| 修正逻辑误改内容字符 | 修复只增删改闭合符；测试期断言按字面量边界分段比对（独立参照物） |
| 把真截断的输入「补」成看似完整的提案 | 条件 2 要求 `rewritten ≥ 1`：不伴随类型错位的真截断必被拦截。**残留**：伴随类型错位的复合形态无法区分，已在「范围收窄声明」显式声明不覆盖 |
| 复合形态产出 operation 数量偏少 | 安全网：产出的是候选提案（不写 `planningDocument`），须作者确认才落库，作者可见内容偏少；见「残余风险与安全网」 |
| 数值字面量被静默改变（如 12345 → 123） | 同上（`rewritten === 0` 时被拦） |
| 中间缺闭合符导致结构错位 | 条件 2 兜住（`rewritten === 0`）；本次显式声明不覆盖 |
| 修正后容器类型与 schema 不符 | 放行条件 4 拦截；类型不符即放弃 |
| 合法 JSON 被误判为字面量未闭合 | 统一转义口径（通用 `escaped` 标志）；用例覆盖 `\\` 结尾与 `\uXXXX` |
| 补齐顺序实现错误产出非法 JSON | 明确 LIFO 顺序；用例断言解析成功 |
| 影响既有 #8 还原路径 | 新逻辑只在 `JSON.parse` 失败分支触发；既有合法 JSON 路径不变，既有 9 个用例必须保持通过 |

## 独立审核门禁

审核需逐条确认：

1. 新逻辑是否严格只增删改闭合符，是否存在任何内容字符被改动的路径。
2. 放行条件 1（字面量完整性）与条件 2（`rewritten ≥ 1` 且 `padded ≤ 1`）是否在所有分支生效（尤其补齐闭合符之前）。
3. 放行条件是否都按固定顺序在最终放行前被检查，而不是部分检查。
4. 扫描是否对超长输入为线性复杂度；输出是否用数组 push + 末尾 join（避免字符串 `+=` 抬高内存峰值）。
5. 是否会与既有 `parseEncodedContainer` 的三条前置判据、既有 `parsePlanningToolJson` 路径产生冲突或重复修复。
6. 反例是否覆盖完整（见「边界与反例」的「必须不修复」表全部 15 项），正例是否覆盖（真实 5 样本形态 + 3 类缺陷组合 + 2 类转义）。
7. 是否未改动 `toolInputIssueHint`、`normalizeToolInput` 的其他分支、schema 定义或任何业务逻辑。
8. 放行条件 2 的判别信号是否在**真实 5 份样本**上成立（`rewritten ≥ 1` 且 `padded ≤ 1`），并对**真截断样本**全部拦截。
9. 「范围收窄声明」与「残余风险与安全网」的表述是否与代码路径一致 —— 特别是 `proposePlanning` 是否确实只写 `contentVersion`（`targetType: "PlanningProposal"`）而不写 `planningDocument`，作者确认环节是否确实存在。
10. 「内容字符未变」是否已正确降级为**测试期断言**，且参照物独立于被测实现。
