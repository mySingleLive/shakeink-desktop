## 二、R1【准阻塞·须先改】反例表与放行条件仍有一处自相矛盾

方案第 187 行（「必须不修复」反例表）：

> `已写错类型 + 后续截断（复合形态） | **不修复**（见「范围收窄声明」，本次明确不覆盖） | 原理上不可区分`

但「范围收窄声明」（第 119 行）承认「该形态下修复**会产出** operation 数量少于模型本意的提案」——即修复器**会放行**它，只是接受残余。实测最小反例（B1）：`rew=1, pad=1, inString=false` → 条件 1/2/3/4 全通过 → **放行**，`operationSchema` 校验通过（ops=1 vs 本意 2）。

表格写「不修复」、正文写「会修复但接受残余」，**实现者按表格写反例用例会期望「拒绝」，按放行条件实现却是「放行」**，用例阶段必然复现该冲突（与 238 N2 同型）。

**必须修改**：把第 187 行的期望行为改为「**放行（已知残余，见范围收窄声明）**」并移出「必须不修复」表，或在表内单列「已接受残余」小节收录该行；同时在第 214 行反例用例清单中**删除**对该形态的「不修复」期望（当前第 214 行未列复合形态，故只需改第 187 行）。

## 三、R2【准阻塞·须先改】「残余风险与安全网」第 2 条代码路径表述不实

逐条核实结果：

- **第 1 点属实**。`proposePlanning`（`planning.ts:545-598`）全函数只有一处写库：`planning.ts:578-587` 的 `db.contentVersion.create({ data: { targetType: "PlanningProposal", … } })`；`planningDocument` 的写入仅在 `commitPlanning`（`planning.ts:320` 的 upsert）中，`proposePlanning` 不调用它，`getPlanning` 读到的当前规划不变。属实。
- **第 2 点表述不实**。「只有作者明确同意后调用 `applyNovelPlanningProposal` 才写入 `planningDocument`」——`applyNovelPlanningProposal` 的 execute（`planning-tools.ts:85-86`）只是 `run(() => applyPlanningProposal(scope, proposalId))`；`applyPlanningProposal`（`planning.ts:619-627`）只校验提案存在与归属（`ownedStory`），**没有任何作者确认的代码校验**。「须经确认」完全由**提示词**承载：工具描述（`planning-tools.ts:81`「只能在作者明确同意后采用…未确认不得采用」）+ `proposePlanning` 回执 message（`planning.ts:595`「立即用 askUserQuestion 列出要点请作者确认…作者明确同意后调用 applyNovelPlanningProposal」）。**模型可在无作者确认时自行调用 `applyNovelPlanningProposal` 落库**，代码层拦不住。面板侧的采用路径（`desktop/handlers/novels/[id]/planning/route.ts:82`）才真正经过作者点击。
- **第 3 点部分属实但依赖模型自律**。「作者可见」的可见性由 `nextPlanningProposalApproval`（`planning.ts:665-679`）与模型的 `askUserQuestion` 承载；若模型不走确认流程、直接 apply，作者只能事后从规划历史察觉，**没有强制的确认面板环节**。
- **第 4 点属实**。实测：截断落在 operation 内部且伴随类型错位（如尾部悬挂 `,`，rew=1, pad=1）修正后 `JSON.parse` 抛 `Unexpected token ']' … not valid JSON` → 条件 3 拦下；截断落在字面量内 → 条件 1 拦下；纯内部截断（rew=0）→ 条件 2 拦下。2 000 例随机变异中放行 190 例、其中 op 数缺失 13 例（6.8%），穿透的均是「整块 operation 缺失」形态，与声明一致。

**须修正的句子**（第 126 行）：

> 原文：「**必须作者确认才落库**。提案保存后返回的 message 明确要求模型用 `askUserQuestion` 列出要点请作者确认；只有作者明确同意后调用 `applyNovelPlanningProposal` 才写入 `planningDocument`。」

建议改为：

> 「**落库路径存在提示词级确认约束，但代码层不强制**。提案保存后返回的 message（`planning.ts:595`）与 `applyNovelPlanningProposal` 的工具描述（`planning-tools.ts:81`）都要求模型先经 `askUserQuestion` 取得作者明确同意才调用 apply；`applyPlanningProposal`（`planning.ts:619-627`）本身不校验确认状态，纯信任模型自律。因此残缺提案会被 `pendingPlanningProposals`（`planning.ts:641-659`，按 `expectedVersion` 匹配当前规划版本）列进 `pendingProposals` 暴露给模型；若模型不守约，可能在无作者确认时自动采用。」

同时评估：安全网强度为「**弱（提示词约束为主）**」，非「强（代码层强制）」。这**不推翻** N1 的取舍（残缺提案仍需一次「模型不自律」才会落库，且落库内容是模型本就输出过的更少内容、不是伪造），但「残余风险」一节的措辞必须从「必须作者确认才落库」这种代码级承诺降为「提示词级约束 + 依赖模型自律」，否则实施后的验证文档会拿错误的事实做安全网证明。

## 四、放行条件 2 单一表述的无歧义性实测（终审重点 5）

按方案文字独立实现后，15 类形态逐条实测（`rew/drop/pad/inStr → 判定`）：

| 形态 | 统计 | 判定 | 与方案声明 |
| --- | --- | --- | --- |
| 真实尾部形态（2 错位 + 多余，~2280 样本） | 2/5/0/false | **放行** ops=1 | 一致 |
| 真实尾部形态（1 错位 + 补齐 1，~2231 样本） | 1/0/1/false | **放行** ops=2 | 一致 |
| 复合形态最小反例（B1） | 1/0/1/false | **放行** ops=1 | 与反例表冲突，见 R1 |
| 仅多余闭合符 | 0/1/0/false | 拒绝(条件 2) | 一致 |
| 仅缺失闭合符 | 0/0/1/false | 拒绝(条件 2) | 一致 |
| 中间缺 `}`（两种形态） | 0/0/1/false | 拒绝(条件 2) | 一致 |
| 错位 + 多层补齐 | 1/0/2/false | 拒绝(条件 2) | 一致 |
| 类型写反 `{"a":1]` | 1/0/0/false | 放行 | 一致（已声明边界） |
| 截断在字面量内 | -/-/-/**true** | 拒绝(条件 1) | 一致 |
| 截断在 op 内部 + 悬挂 `,` + 错位 | 1/0/1/false | **拒绝(条件 3)** parse 失败 | 一致（第 128 行声明成立） |
| 合法 JSON（含 `\\` 结尾 / 中文 / `\uXXXX`） | 0/0/0/false | 拒绝(条件 2) 不触发 | 一致（既有路径不回归） |

**结论：无歧义。** 每类形态按「字面量完整 → `rew≥1 ∧ pad≤1` → parse → 类型一致」固定顺序求值得到唯一结论；`dropped` 不参与放行（实测真实样本含 drop=1 仍放行，方案第 98 行自洽）。补充：2 000 例随机变异（3-op 合法文档注入 1 处类型错位 + 随机截断）中放行 190、拦截 1 810，放行例中 op 数缺失 13 例，全部为「整块 operation 缺失」形态，无「内容字符被改」与「结构错吸」（骨架比对 0 例不一致）——N1 残余的规模与方案声明相符（只丢整块，不改内容）。

## 五、门禁 5 降级后的完整性与建议（终审重点 6）

测试期断言 + 独立参照物足以保证实现正确性，理由：（a）断言只在测试期运行，无运行时开销与共因风险；（b）独立参照实现（如 `JSON.parse` 后递归剔除字面量内闭合符、或逐字面量切分）与被测扫描器的失败模式不重叠，238 已实证独立扫描器可检出共因漏检。建议在用例阶段补充两条更强的测试期手段：

1. **随机变异对比（差分测试）**：以合法 JSON 为种子，随机注入「闭合符替换/删除/插入/截断」，对放行例断言「骨架（字面量外剔除闭合符后）与原串逐字符一致」+「parse 结果 op 数 ≤ 原 op 数」；对拒绝例断言返回 `undefined`。本次 2 000 例已验证该方法可在秒级完成，适合作为固定用例（固定种子保证可复现）。
2. **元缺陷注入**：对 3 类典型错误实现（忘记字面量状态、FIFO 补齐、把字面量内闭合符计入 rewritten）逐一跑测试集，断言测试集**能抓住**每一种——这直接验证用例集的判别力，而非只验证正确实现通过。
